<objective>
## Goal
Add the DailyInventory (shared room-type-level availability) and RatePlanDailyRate (per-rate-plan price/minStay) models, and a 365-day seed worker that populates both correctly for a given RoomType.

## Purpose
This is the actual "source of truth calendar" the whole product is built around. Getting the shared-vs-per-rate-plan split right here is what prevents the same physical room from being sold twice through two different rate plans — the project's #1 stated success metric (zero overbookings) depends on this being correct at the schema level, not patched later.

## Output
Two new tables migrated against the real dev database, a reusable seed function, and proof — via a real inserted RoomType with two RatePlans — that 365 days of shared inventory and per-rate-plan rates seed correctly and idempotently.
</objective>

<acceptance_criteria>

## AC-1: Availability is shared across rate plans of the same room type, not independent per rate plan
```gherkin
Given a RoomType with 3 physical Rooms and two RatePlans (Refundable, Non-Refundable)
When the seed worker runs for that RoomType
Then exactly one DailyInventory row exists per date with availableCount 3 — not one row per (RoomType, RatePlan) pair — and both RatePlans share that same count
```

## AC-2: Rate plans have independent price/minStay, not independent availability
```gherkin
Given the same RoomType with two RatePlans
When the seed worker runs
Then RatePlanDailyRate has one row per (RatePlan, date) with that rate plan's own price and minStay, with no availableCount field on this table at all
```

## AC-3: Seed covers exactly 365 days from today in Asia/Manila time
```gherkin
Given the seed worker runs today
When the resulting DailyInventory rows are counted for the RoomType
Then there are exactly 365 rows, starting from today's date in Asia/Manila (not UTC), with no gaps or duplicates
```

## AC-4: Seed worker is idempotent
```gherkin
Given the seed worker has already run once for a RoomType
When it is run again without clearing data first
Then it completes successfully with no duplicate rows and no unique-constraint errors — existing dates are left as-is, not overwritten
```

<!-- audit-added -->
## AC-5: The database itself refuses to let bookings exceed physical availability
```gherkin
Given a DailyInventory row with availableCount 3
When an update attempts to set bookedCount + heldCount to a value greater than 3
Then the database rejects the write via a CHECK constraint — this must hold even if application code has a bug, not rely on Phase 2's transaction logic alone
```

<!-- audit-added -->
## AC-6: Seeding a RoomType with zero physical rooms does not error
```gherkin
Given a RoomType with no active Rooms yet (a hotel admin created the room type before adding rooms — a normal Phase 3 workflow order)
When the seed worker runs for that RoomType
Then it completes successfully, producing 365 DailyInventory rows with availableCount 0, not an error or a skipped seed
```

<task type="auto">
  <name>Task 1: Add DailyInventory and RatePlanDailyRate models, migrate</name>
  <files>prisma/schema.prisma</files>
  <action>
    Add to prisma/schema.prisma:

    - model DailyInventory: id (cuid), hotelId FK -> Hotel onDelete: Restrict (denormalized, same pattern as RatePlan in 01-01), roomTypeId FK -> RoomType onDelete: Restrict, date (DateTime @db.Date — calendar date only, no time component, avoids timezone ambiguity in storage), availableCount Int, bookedCount Int @default(0), heldCount Int @default(0), isClosed Boolean @default(false), createdAt, updatedAt.
      @@unique([roomTypeId, date]) — one row per room type per day, this is the shared pool.
      @@index([hotelId])

    - model RatePlanDailyRate: id (cuid), hotelId FK -> Hotel onDelete: Restrict (denormalized), ratePlanId FK -> RatePlan onDelete: Restrict, date (DateTime @db.Date), price Decimal @db.Decimal(10,2), minStay Int @default(1), createdAt, updatedAt.
      @@unique([ratePlanId, date]) — one row per rate plan per day.
      @@index([hotelId])
      Deliberately no availableCount/bookedCount/heldCount on this model — those live only on DailyInventory, shared across all rate plans of the room type.

    - Add `basePrice Decimal @db.Decimal(10,2)` to the existing RatePlan model — the default price the seed worker uses to populate RatePlanDailyRate rows. Requires a migration on an existing table; since no real hotel data exists yet (only smoke-test rows from 01-01), this is safe now and would not be after real rate plans exist.

    Note: DailyInventory and RatePlanDailyRate intentionally do NOT get a deletedAt soft-delete column, unlike 01-01's models — these are calendar grid rows, not entities with a lifecycle. The correct domain operation for "this date shouldn't be sold" is isClosed = true (stop-sell), not deletion. Deleting rows would create date gaps the whole system isn't designed to handle.

    <!-- audit-added --> All monetary values (RatePlan.basePrice, RatePlanDailyRate.price) are PHP — no currency column exists or is needed while the project is PH-only per PROJECT.md scope. Add this as a comment directly above both fields in schema.prisma so a future reader doesn't have to guess.

    Run: npx prisma migrate dev --name add_daily_inventory_and_rate_plan_rates

    <!-- audit-added --> Then run a second, constraint-only migration: `npx prisma migrate dev --name add_inventory_check_constraints --create-only` (Prisma's schema DSL does not reliably express multi-column CHECK constraints across versions — do this via a raw SQL migration instead of forcing it into schema.prisma). Edit the generated empty migration.sql to add:
    - On DailyInventory: `CHECK ("availableCount" >= 0 AND "bookedCount" >= 0 AND "heldCount" >= 0 AND "bookedCount" + "heldCount" <= "availableCount")` — this is the actual database-level backstop against overbooking. It must exist before Phase 2 builds booking logic on top of this table, not added after real bookings exist, because retrofitting a CHECK constraint onto a table that may already contain violating rows requires a data cleanup pass first.
    - On RatePlanDailyRate: `CHECK ("minStay" >= 1)`
    - On RatePlan: `CHECK ("basePrice" > 0)`
    Then run `npx prisma migrate dev` (without --create-only) to apply it.
  </action>

  <action>
    In src/lib/seed-inventory.ts, export an async function `seedInventoryForRoomType(roomTypeId: string): Promise<{ daysCreated: number; daysSkipped: number }>`:
    - Load the RoomType (with hotelId), count its active (deletedAt: null) Rooms to compute availableCount, and load all active RatePlans for that RoomType.
    - Compute "today" as a calendar date in Asia/Manila (use a fixed UTC+8 offset calculation or an Asia/Manila-aware date library call — do not use the server's local timezone or raw `new Date()` at midnight UTC, which would be the wrong calendar day for part of the Philippine day).
    - For each of the next 365 days (today through today+364): if a DailyInventory row for [roomTypeId, date] does not already exist, create one with the computed availableCount, bookedCount 0, heldCount 0, isClosed false. If it already exists, skip it (do not overwrite — idempotency requirement).

Then call seedInventoryForRoomType a second time and confirm daysCreated is 0 and daysSkipped is 365 (proving idempotency), with no errors.

    Avoid: computing "today" from the server's raw local timezone — this machine and any eventual deployment target may not be in Asia/Manila, and getting this wrong silently shifts the entire grid by a day at certain hours.
