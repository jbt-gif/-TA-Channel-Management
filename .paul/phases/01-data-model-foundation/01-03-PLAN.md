<objective>
## Goal
Add the last core models for Phase 1 — Guest, Booking, BookingItem, Payment, ChannelMapping — completing the data model foundation with the multi-tenant isolation pattern applied consistently, and a schema shape that already carries what Phase 2 (atomic booking transactions) and Phase 4 (Channex sync) will need without building that logic now.

## Purpose
This is the last plan in Phase 1. Every later phase builds directly on these five models: Phase 2 creates Bookings/BookingItems inside an atomic transaction, Phase 4 reads/writes Booking via ChannelMapping and needs webhook-idempotency fields already present, Phase 5 creates Payment rows against a real Xendit reference. Getting the shape (not the behavior) right now avoids retrofitting a schema after real bookings and payments exist.

## Output
Five new models migrated against the real dev database, financial/audit-correct field choices (price snapshots, status enums instead of soft-delete where deletion would destroy history), DB-level CHECK constraints on the values that must never go negative or backwards, and a real end-to-end smoke test proving a full Guest → Booking → BookingItem → Payment chain can be created and correctly hotel-scoped.
</objective>

## AC-1: All five new models follow the established multi-tenant isolation pattern
```gherkin
Given Guest, Booking, BookingItem, Payment, and ChannelMapping are added to the schema
When the schema is reviewed
Then every model has a non-nullable hotelId, a cuid() id, onDelete: Restrict on every foreign key, and an @@index([hotelId]) — matching the pattern established in 01-01/01-02
```

## AC-2: A full booking chain can be created and correctly linked
```gherkin
Given a Hotel with a Guest, a RoomType with two RatePlans, and Rooms
When a Booking is created with two BookingItems (one per RatePlan) and a Payment
Then all rows are created successfully, correctly hotelId-scoped, and traceable from Payment back to Booking back to Guest
```

## AC-3: Booking cancellation never destroys history
```gherkin
Given a Booking exists
When it is cancelled
Then its status changes to CANCELLED via the BookingStatus enum — the row is never soft-deleted or hard-deleted, because bookings are financial/audit records that must remain queryable
```

## AC-4: BookingItem carries a total price snapshot, not a live price reference
```gherkin
Given a BookingItem is created with totalPriceSnapshot computed from the RatePlan's RatePlanDailyRate price(s) at booking time (3500 for a 1-night stay)
When RatePlanDailyRate.price later changes to 4000 for that date
Then the BookingItem's own totalPriceSnapshot remains 3500 — historical bookings must not silently change value when rates are edited later
```

## AC-7: Booking and Payment record which staff member acted, when known
```gherkin
Given a walk-in Booking is created by a FRONT_DESK user, and a Payment is processed by that same user
When the rows are queried
Then Booking.createdByUserId and Payment.processedByUserId reference that User — nullable, since Phase 4 OTA bookings and Phase 5 webhook-driven payments have no staff actor
```

## AC-5: ChannelMapping can link either a RoomType or a RatePlan to an external Channex id
```gherkin
Given Phase 4 will need to map local RoomTypes/RatePlans to Channex-side ids
When a ChannelMapping row is created for a RoomType and another for a RatePlan
Then both are stored with a mappingType discriminator and the external id, ready for Phase 4 to read/write without this plan implementing any Channex API calls
```

## AC-6: The database rejects structurally invalid data even if application code has a bug
```gherkin
Given the new CHECK constraints are live
When an attempt is made to insert a BookingItem with checkOutDate <= checkInDate, a non-positive quantity, or non-positive totalPriceSnapshot, a Payment with a non-positive amount, or a Booking with a non-positive totalAmount (when set)
Then the database rejects the write
```
