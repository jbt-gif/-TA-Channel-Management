## 1. Executive Verdict

Not enterprise-ready as originally written — solid bones, but five release-blocking gaps that are cheap to fix now and expensive to fix after real data exists. All five have been applied to the plan below. As amended, this plan is acceptable to build against.

Would I sign my name to shipping the *original* version to a database that would later hold real tenants? No — sequential IDs, undefined cascade-delete behavior, and no soft-delete path are exactly the kind of foundation-phase shortcuts that turn into painful migrations six months in, once real hotel data is sitting on top of them. Would I sign the amended version below? Yes, for a Phase 1 foundation plan.

## 2. What Is Solid (Do Not Change)

- **Every hotel-owned table explicitly carries hotelId, not inferred through some implicit tenant context.** This is the correct default for a multi-tenant system — isolation should be structurally visible in the schema, not something a developer has to remember to add via middleware.
- **The plan verifies against a real database, not a mock or an assumption.** Task 2's verify step runs an actual migration and an actual insert/read cycle against the real Supabase dev instance. This matches the project's own stated principle (don't trust a claim — run it) and is exactly right for a foundation phase where a schema that merely "looks correct" is not the same as one that's been proven correct.
- **The checkpoint for pasting real credentials into .env, rather than having them pass through this conversation or get generated by an agent, is correctly placed and correctly scoped** — a genuine human-action step, not busywork.
- **Scope boundaries are explicit and appropriately narrow** (no DailyInventory, no Booking, no auth flow, no frontend) — this plan does not try to do too much in one pass.

## 3. Enterprise Gaps Identified

1. **Enumerable primary keys.** No ID generation strategy was specified, meaning Prisma's default (auto-incrementing integer) would apply. Once API routes exist in Phase 2, sequential IDs let anyone enumerate adjacent resources (hotel 1, hotel 2, hotel 3...) — a real authorization-boundary weakness, and one that's essentially impossible to retrofit later without breaking every external reference (Channex ChannelMapping IDs, Xendit payment references) built on top of it.

2. **Undefined foreign-key delete behavior.** No `onDelete` behavior was specified on any tenant-scoping foreign key. Prisma/Postgres defaults vary and are easy to get wrong silently — an accidental `Hotel` delete could cascade-erase an entire tenant's data with no explicit decision ever having been made about whether that's acceptable. This is precisely the "state ambiguity / invalid transition" category a real audit would flag.

3. **No soft-delete or deactivation path.** `Hotel`, `User`, `RoomType`, and `Room` had no way to be deactivated or soft-deleted — only hard delete (implicitly, via whatever the undefined cascade behavior did). The project's own PROJECT.md and app-build-sop.md both already commit to "soft deletes / audit log on anything destructive" as a standing rule; the schema didn't reflect it. Retrofitting this after real rows exist means a migration plus auditing every existing query — trivial now, painful later.

4. **RatePlan's tenant isolation required an implicit join.** `RatePlan` only reached `hotelId` transitively through `RoomType`. Every future query needing to enforce "this rate plan belongs to this hotel" would need to remember to join through `RoomType` correctly — a missed join is exactly the kind of bug that leaks one hotel's rate data into another hotel's view. Silent multi-tenant data leakage is a release-blocking category of risk for a system whose entire value proposition depends on strict per-hotel isolation.

5. **Unproven repeatability of the only verification script.** The smoke-test script as originally scoped had no idempotency requirement — running it a second time (e.g., after fixing an unrelated bug) would fail on the unique email constraint. A verification step that can only be trusted once isn't a reliable verification step; this undermines the project's own "don't trust an unverified claim" principle applied to its own tooling.

**Lower-severity, still worth noting:**
- No `@@unique` constraint preventing two rooms in the same hotel from sharing a room label, or two room types sharing a name — a data-integrity gap that would confuse the admin UI being built in Phase 3.
- `passwordHash` exists as a column with no explicit statement that it must never hold plaintext, even though hashing logic itself correctly doesn't ship until the login phase.

## 4. Upgrades Applied to Plan

### Must-Have (Release-Blocking)

| # | Finding | Plan Section Modified | Change Applied |
|---|---------|----------------------|-----------------|
| 1 | Enumerable primary keys | Task 2 action | Every model now specifies `@id @default(cuid())`; AC-3 updated to require non-sequential IDs |
| 2 | Undefined FK delete behavior | Task 2 action | Every tenant-scoping FK now specifies `onDelete: Restrict`, with the rationale (no silent cascade-delete of a tenant's data) stated inline |
| 3 | No soft-delete path | Task 2 action | `deletedAt DateTime?` added to Hotel, User, RoomType, Room (nullable = active) |

## 5. Audit & Compliance Readiness

- **Audit evidence:** with `createdAt`/`updatedAt` on every model and non-enumerable IDs, individual records are traceable without being guessable. `deletedAt` (added above) preserves history instead of destroying it on deactivation — this is what supports later post-incident reconstruction, which the original version did not.
- **Silent failure prevention:** the `onDelete: Restrict` addition is the single most important compliance-relevant change here — without it, a tenant's entire dataset could vanish with no explicit failure, no log, no decision trail. Restrict forces any accidental cascade to fail loudly instead.
- **Ownership/accountability:** every hotel-owned row is now unambiguously traceable to exactly one hotelId at the schema level, including RatePlan — this is the structural basis for per-tenant accountability in every later phase.
- **Would this fail a real audit as originally written?** Yes, specifically on cascade-delete behavior and lack of soft-delete — both are standard checklist items in any SOC2-adjacent review of a multi-tenant system. As amended, both are addressed.

## 6. Final Release Bar

**What must be true before this plan (as amended) ships:** all five must-have items must actually be implemented and verified in Task 2, not just described in the plan — the audit only strengthens the document, APPLY still has to deliver it, and `/paul:verify` still has to confirm it with real eyes on real output.

**What risk remains if shipped as amended:** none release-blocking at this phase's scope. The two deferred items are genuinely low-risk at this stage and correctly scoped to later phases.

**Sign-off:** yes, as amended. The original plan would not have passed; a foundation-phase schema with enumerable IDs, undefined cascade behavior, and no soft-delete path is not something I'd stand behind for a system meant to carry real hotel tenants and real guest data six phases from now.
