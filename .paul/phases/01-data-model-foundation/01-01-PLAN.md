<objective>
## Goal
Stand up the backend project (Node/Express/TypeScript/ESM) and define the core Prisma schema — Hotel, User (with roles), RoomType, RatePlan, Room — migrated against a real Supabase Postgres dev database.

## Purpose
Everything in this project depends on this schema existing and being correct. This is the foundation phase — no UI, no booking logic yet, just the data model that every later phase builds on.

## Output
A working backend project that boots, connects to the real dev database, and has the first 5 core tables migrated and verified with real inserted data — not just a schema file that's never been run.

<task type="auto">
  <name>Task 2: Define core Prisma schema and migrate against real dev database</name>
  <files>prisma/schema.prisma, src/scripts/smoke-test.ts</files>
  <action>
    In prisma/schema.prisma, set datasource db to use env("DATABASE_URL") with directUrl = env("DIRECT_URL").
    <!-- audit-added --> Verify DATABASE_URL includes the query param `?pgbouncer=true` (Supabase's Transaction pooler URI includes this by default when copied from the dashboard; if the value pasted into .env is missing it, append it). Required because Prisma Client must disable prepared-statement caching to work correctly against PgBouncer's transaction-mode pooling — omitting this causes confusing runtime failures, not a clean error.
    <!-- audit-added --> Every model's id field: `@id @default(cuid())`, not an auto-incrementing integer. Sequential integer IDs make resources enumerable once API routes exist in Phase 2 (an attacker or curious user could guess adjacent hotel/booking IDs) — cheap to get right now, effectively impossible to change later without a painful migration once real data and external references (Channex ChannelMapping IDs, Xendit references) exist.
    Define:
    - enum Role { SUPER_ADMIN HOTEL_ADMIN FRONT_DESK HOUSEKEEPING }
    - enum HousekeepingStatus { CLEAN DIRTY INSPECTING OUT_OF_SERVICE }
    - model Hotel (id, name, timezone default "Asia/Manila", <!-- audit-added --> deletedAt DateTime? (nullable, null = active), createdAt, updatedAt)
    - model User (id, hotelId FK -> Hotel <!-- audit-added --> onDelete: Restrict, email unique globally across the whole platform — <!-- audit-added --> this is a deliberate decision: a person's email identifies them uniquely platform-wide, not just within one hotel, so two different hotels cannot register the same staff email, passwordHash, role Role, <!-- audit-added --> deletedAt DateTime? (staff deactivation, not hard delete), createdAt, updatedAt)
    - model RoomType (id, hotelId FK -> Hotel <!-- audit-added --> onDelete: Restrict, name, baseCapacity, <!-- audit-added --> deletedAt DateTime?, createdAt, updatedAt) <!-- audit-added --> — add @@unique([hotelId, name]) so two room types in the same hotel can't silently share a name
    - model RatePlan (id, roomTypeId FK -> RoomType <!-- audit-added --> onDelete: Restrict, <!-- audit-added --> hotelId FK -> Hotel onDelete: Restrict (denormalized, redundant with roomTypeId's own hotelId — added deliberately so tenant-isolation queries never require a join through RoomType to enforce hotel scoping; this closes a class of "forgot to join and check tenant" bugs before Phase 2 builds query patterns on top of it), name, isRefundable Boolean, includesBreakfast Boolean, <!-- audit-added --> deletedAt DateTime?, createdAt, updatedAt)
    - model Room (id, hotelId FK -> Hotel <!-- audit-added --> onDelete: Restrict, roomTypeId FK -> RoomType <!-- audit-added --> onDelete: Restrict, label e.g. "101", housekeepingStatus HousekeepingStatus default CLEAN, <!-- audit-added --> deletedAt DateTime?, createdAt, updatedAt) <!-- audit-added --> — add @@unique([hotelId, label]) so two rooms in the same hotel can't share a room number
    Every hotel-owned model (User, RoomType, RatePlan, Room) carries an explicit hotelId column and foreign key — this is the multi-tenant isolation pattern every later query must filter on.
    <!-- audit-added --> Every foreign key referencing Hotel or RoomType uses onDelete: Restrict, not the Prisma default — an accidental Hotel or RoomType delete must fail loudly, never silently cascade-delete a hotel's entire dataset.
    <!-- audit-added --> passwordHash: this plan does not implement login, but the column must never receive plaintext even in test/smoke data — treat it as a real credential field from the moment it exists, not just once auth logic ships.
    Add index on User.hotelId, RoomType.hotelId, Room.hotelId, Room.roomTypeId, RatePlan.hotelId, RatePlan.roomTypeId.
    Run: npx prisma migrate dev --name init_core_schema
    Then write src/scripts/smoke-test.ts: a standalone script using the Prisma client to create one Hotel, one User per Role value, one RoomType, one RatePlan, one Room, then read them back and print confirmation. Attempt one deliberately invalid insert (bad enum value) wrapped in try/catch to confirm the database rejects it. <!-- audit-added --> Make the script idempotent: either upsert on a fixed known key (e.g. hotel slug), or delete any previously-created smoke-test records for this hotel before inserting fresh ones — it must be safe to run repeatedly without failing on unique-constraint violations (email, hotelId+name, hotelId+label).
    Avoid: making hotelId nullable or optional anywhere — every hotel-owned row must always have one, that's the isolation boundary. Avoid: auto-incrementing integer IDs. Avoid: any onDelete behavior other than Restrict without explicit justification written in a code comment.
  </action>
  <verify>npx prisma migrate dev completes with no errors against the real Supabase dev database; npx tsx src/scripts/smoke-test.ts runs twice in a row and prints successful inserts for all 5 models both times, plus confirmation that the invalid enum insert was rejected</verify>
