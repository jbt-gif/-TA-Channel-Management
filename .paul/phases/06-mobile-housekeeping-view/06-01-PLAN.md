<objective>
## Goal
Housekeeping staff can view all rooms for their hotel and update a room's status (CLEAN/DIRTY/INSPECTING/OUT_OF_SERVICE) from a phone-sized screen, tenant-scoped and role-gated.

## Purpose
Closes Phase 6, the last unbuilt v0.1 feature besides the resequenced PayMongo phase. `Room.housekeepingStatus` and the `HousekeepingStatus` enum already exist in the schema (Phase 1) and are read nowhere and written nowhere yet — this plan is the first consumer.

## Output
- `GET /api/rooms` and `PATCH /api/rooms/:roomId` — tenant-scoped, HOUSEKEEPING/HOTEL_ADMIN/SUPER_ADMIN roles
- `/housekeeping` mobile-first React page — room list grouped by room type, tap-to-cycle or select status
</objective>


## AC-3: Update room status (authorized role)
```gherkin
Given an authenticated HOUSEKEEPING, HOTEL_ADMIN, or SUPER_ADMIN user, and a Room belonging to their own hotel
When they PATCH /api/rooms/:roomId with { housekeepingStatus: "DIRTY" }
Then the room's housekeepingStatus updates, lastChangedByUserId is set to the acting user's id, lastChangedAt is set to the current time, and the response reflects all three
```
<!-- audit-added: lastChangedByUserId/lastChangedAt clause -->

## AC-3a: GET is intentionally open to any authenticated role
```gherkin
Given an authenticated FRONT_DESK user (not HOUSEKEEPING/HOTEL_ADMIN/SUPER_ADMIN)
When they call GET /api/rooms
Then they receive the room list successfully (200) — GET is read-only and carries no mutation risk, so it is not role-restricted the way PATCH is; only PATCH is role-gated
```
<!-- audit-added: makes the GET/PATCH role asymmetry an explicit, testable decision instead of an implicit one a future reader has to infer -->

## AC-3b: No-op status resubmit does not overwrite the accountability trail
```gherkin
Given a Room whose lastChangedByUserId/lastChangedAt already reflect a prior real change
When any authorized user PATCHes it with the SAME housekeepingStatus it already has
Then lastChangedByUserId and lastChangedAt remain exactly as they were — the true record of who last actually changed the status is preserved
```
<!-- plan-critic-added: a same-value re-tap is normal usage under Task 3's always-visible-buttons UI, not an edge case — without this, the accountability fields the audit added would be silently corrupted by routine use -->

## AC-4: Reject unauthorized role
```gherkin
Given an authenticated FRONT_DESK user
When they PATCH /api/rooms/:roomId
Then the request is rejected with 403 and the room's status is unchanged
```

## AC-5: Reject invalid status value
```gherkin
Given an authenticated HOUSEKEEPING user
When they PATCH /api/rooms/:roomId with { housekeepingStatus: "SPOTLESS" }
Then the request is rejected with 400 and the room's status is unchanged
```

## AC-6: Cross-tenant isolation on update
```gherkin
Given a user authenticated for hotel A
When they PATCH /api/rooms/:roomId where roomId belongs to hotel B
Then the request returns 404 (not 403 — existence must not leak), and hotel B's room is unchanged
```

<task type="auto">
  <name>Task 2: Rooms API — list + status update</name>
  <files>src/routes/rooms.ts, src/app.ts</files>
  <action>
    Create `src/routes/rooms.ts` following `src/routes/roomTypes.ts`'s established pattern exactly (requireAuth, tenant-scoped `findFirst`/`findMany` with `hotelId: req.auth!.hotelId, deletedAt: null`, try/catch scoped around the whole ownership-check-through-response block, generic 500 on unexpected error, identical 404 body whether the id doesn't exist or belongs to another hotel).

    `GET /` (requireAuth only, any role — intentional, see AC-3a: read-only, no mutation risk):
    - `prisma.room.findMany({ where: { hotelId: req.auth!.hotelId, deletedAt: null }, include: { roomType: { select: { name: true } } } })`
    - Return `[{ id, label, roomTypeId, roomTypeName: roomType.name, housekeepingStatus, lastChangedByUserId, lastChangedAt }]`, sorted by roomTypeName then label (stable grouping for the frontend — do this in the query with `orderBy` or in-memory, either is fine).

    `PATCH /:roomId`:
    - Role gate: only HOUSEKEEPING, HOTEL_ADMIN, SUPER_ADMIN (`const ALLOWED_ROLES = new Set(["HOUSEKEEPING", "HOTEL_ADMIN", "SUPER_ADMIN"])`, checked before the DB call, same as roomTypes.ts's `ADMIN_ROLES` pattern) — 403 with generic `{ error: "Forbidden" }` if not.
    - Body: `{ housekeepingStatus: string }`. Validate it's exactly one of `["CLEAN", "DIRTY", "INSPECTING", "OUT_OF_SERVICE"]` (import the literal set, do not trust the Prisma enum to reject a bad string silently — Prisma will throw on invalid enum value, but a validated 400 is a better UX than a 500 from an uncaught Prisma error). 400 with `{ error: "housekeepingStatus must be one of CLEAN, DIRTY, INSPECTING, OUT_OF_SERVICE" }` if missing or invalid.
    - `findFirst({ where: { id: roomId, hotelId: req.auth!.hotelId, deletedAt: null } })` for the ownership check; 404 with `{ error: "Room not found" }` if absent (covers both "doesn't exist" and "belongs to another hotel" — same tenant-isolation discipline as roomTypes.ts).
    - <!-- plan-critic-added: only re-stamp the accountability fields when the value actually changes --> Compare the validated `housekeepingStatus` to the fetched room's current value. If unchanged, skip the update entirely and return 200 with the room as-is (no-op — a same-value tap must not overwrite who/when actually changed it). If changed, `prisma.room.update({ where: { id: roomId }, data: { housekeepingStatus, lastChangedByUserId: req.auth!.userId, lastChangedAt: new Date() } })` and return 200 with the updated room `{ id, label, roomTypeId, housekeepingStatus, lastChangedByUserId, lastChangedAt }`. **Why this matters:** the accountability fields exist specifically to answer "who last changed this room's status" for a guest-quality dispute — unconditionally re-stamping on every PATCH (including a housekeeper re-tapping the same status to confirm what they see on screen) would silently overwrite the true answer with whoever happened to touch it last, which is worse than having no record at all.

    Mount in `src/app.ts`: `app.use("/api/rooms", roomsRouter)` alongside the other `/api/*` routers (after `express.json()`, same section as roomTypes/ratePlans/bookings/hotel/sync-status).
  </action>
  <verify>
    Start backend, obtain a JWT for a seeded HOUSEKEEPING user and a seeded HOTEL_ADMIN user for hotel A, and one for a user on hotel B (or reuse an existing seeded second hotel if one exists in dev data — otherwise create one throwaway room on a second hotelId directly via Prisma for the isolation check only).
    - GET /api/rooms as hotel A user → 200, only hotel A's rooms, includes roomTypeName
    - GET /api/rooms as a FRONT_DESK user → 200 (confirms AC-3a's intentional non-gating)
    - PATCH as HOUSEKEEPING with valid status → 200, DB row updated including lastChangedByUserId = the HOUSEKEEPING user's id and lastChangedAt within the last few seconds (verify via a follow-up GET or direct Prisma read)
    - PATCH again with the SAME status → 200, but lastChangedByUserId/lastChangedAt UNCHANGED from the previous check (confirms the no-op fix)
    - PATCH as FRONT_DESK → 403, DB row unchanged (including lastChangedByUserId/lastChangedAt unchanged)
    - PATCH with housekeepingStatus: "SPOTLESS" → 400, DB row unchanged
    - PATCH a hotel-B room's id using hotel-A's token → 404, hotel B's row unchanged
  </verify>
  <done>AC-1, AC-2, AC-3, AC-3a, AC-3b, AC-4, AC-5, AC-6 satisfied</done>
