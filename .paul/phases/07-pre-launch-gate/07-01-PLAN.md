<objective>
## Goal
Stand up a real staging environment (backend + frontend, both live on the internet) separate from a real, schema-complete production database — closing the "no deployment exists at all" gap and the long-standing CORS deferred issue in the same pass.

## Purpose
ROADMAP.md's Phase 7 lists "staging environment separate from production" as a named Success Metric. Nothing in this project has ever been deployed — every prior checkpoint (02-04 through 06-01) was verified against `localhost` via Vite's dev proxy, which silently avoids CORS entirely. The 02-04 audit flagged this explicitly: CORS will block every real API call once frontend and backend sit on different origins. This plan is where that stops being deferred.

User-confirmed sequencing (2026-08-28): promote the current Supabase project to be the permanent staging database (not a throwaway); create a separate, new Supabase project for production, schema-complete but not necessarily kept always-running pre-revenue (cost-conscious — no real hotel exists yet to serve).

## Output
- CORS middleware on the backend, origin-allowlisted via env var, fail-fast validated at startup (matching the existing `JWT_SECRET` startup-check convention)
- Backend deployed to Render (free tier), pointed at the (promoted) staging Supabase project
- Frontend deployed to Vercel (free tier), pointed at the Render staging backend
- A second, new Supabase project for production, schema-complete (`prisma migrate deploy` applied), proving the separation is real — not yet serving live traffic
</objective>

  <name>Task 1: CORS middleware + fail-fast origin validation</name>
  <files>src/app.ts, src/middleware/cors.ts, package.json, .env.example</files>
  <action>
    Install `cors` (+ `@types/cors` as a dev dependency).

    Add `CORS_ORIGIN` to `.env.example` with a comment explaining it's a comma-separated allowlist of exact origins (scheme+host+port, no wildcard, no trailing slash) — e.g. `https://your-staging-app.vercel.app`.

    Create `src/middleware/cors.ts`: at module load, read `process.env.CORS_ORIGIN`, split on commas, trim, reject (throw, causing `process.exit(1)` the same way `src/lib/auth.ts`'s `JWT_SECRET` check does) if the result is empty or any entry fails `new URL(entry)` (catches malformed input) or has a trailing slash (catches `https://x.com/` silently never matching a real request's `https://x.com` Origin header — a common, easy-to-miss self-inflicted CORS bug). Export a configured `cors()` middleware instance using that allowlist (reject any Origin not in the list; do not use `cors()`'s permissive `origin: true`/`*` default).

    Wire it into `src/app.ts` — mounted before `express.json()`, after the Channex webhook route (that route has no Origin header at all, being server-to-server; CORS is irrelevant to it and must not gate it).

    <!-- audit-added: real production-breaking gap, confirmed by grepping src/routes/auth.ts --> Also add `app.set("trust proxy", 1)` in `src/app.ts` (near the top, before any middleware). Render sits in front of the app as a reverse proxy; without this, Express's `req.ip` resolves to Render's proxy address for every request, not the real client — which breaks Phase 2's login rate limiter (`src/routes/auth.ts`'s `loginLimiter`, keyed on the default `req.ip`) by collapsing every visitor into one shared bucket: 5 login attempts from anyone locks out the entire staging environment for 15 minutes. `trust proxy: 1` trusts exactly one hop (Render's own proxy), not an arbitrary chain — do not set it to `true`/unbounded, which would let a client forge its own `X-Forwarded-For` and bypass the rate limit entirely.

    Avoid: `Access-Control-Allow-Origin: *` (would defeat the point — this project's stated compliance discipline treats guest data with real regard even pre-formal-compliance-regime), and reading `CORS_ORIGIN` lazily per-request instead of validating once at startup (would let a bad config serve broken CORS silently for a while instead of failing loud immediately, contradicting this project's zero-silent-failures convention).
  </action>
  <verify>
    Start the backend with `CORS_ORIGIN` unset → process exits with a clear error, not a hang or a silent listen.
    Start it with `CORS_ORIGIN=http://localhost:5173` → `curl -H "Origin: http://evil.example" -I http://localhost:3000/api/rooms` (with a valid token) shows no `Access-Control-Allow-Origin` header for that origin; the same request with `Origin: http://localhost:5173` shows it echoed back correctly.
    Confirm `app.set("trust proxy", 1)` is present in `src/app.ts`.
  </verify>
  <done>AC-1, AC-2 satisfied</done>

## DO NOT CHANGE
- `frontend/src/lib/api.ts` — its `VITE_API_URL` fallback logic already anticipated this deployment; no code change needed, only Vercel's env var config
- Any existing route handler logic — this plan is deployment/CORS plumbing only, not a feature or bug-fix plan

## SCOPE LIMITS
- No production app-tier deployment (backend/frontend) — only the production database gets stood up and schema-verified, per the cost-conscious decision above; deploying prod's app tier is a same-shape, low-effort follow-up whenever a real hotel actually onboards, not scheduled as its own plan
- No CDN/custom-domain setup — Render's/Vercel's default `*.onrender.com`/`*.vercel.app` URLs are sufficient for a staging environment; custom domains are a pre-real-launch concern, not this plan's
- No CI/CD pipeline (auto-deploy on push) configuration beyond whatever Render/Vercel do by default when connected to the repo — a dedicated CI setup is out of scope
- **Known, accepted limitation, not fixed here (plan-critic-surfaced, user-confirmed 2026-08-28):** the `PushQueue` background worker (`src/lib/pushQueueWorker.ts`) runs as an in-process `setInterval`, not a separate always-on process. Render's free tier sleeps after ~15 min idle, which stops the worker until an unrelated HTTP request wakes the container again — Channex ARI sync silently pauses while staging is idle. Accepted for staging now (no real hotel's data depends on timely sync yet); logged as a Deferred Issue for production's topology to resolve for real before a paying hotel goes live (options: keep-warm ping, a paid always-on tier, or moving the worker to its own process) — not silently inherited by copying staging's deploy shape unexamined.

</boundaries>
