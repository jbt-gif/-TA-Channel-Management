<objective>
## Goal
Front-desk staff can create a real walk-in booking from the browser — the last piece closing Phase 2's full loop: see availability (02-05) → create a booking (this plan) → see the grid immediately reflect the new, reduced availability.

## Purpose
02-03 built the atomic, overbooking-safe booking transaction; 02-05 made availability visible. Neither is usable by an actual human yet. This is the last plan of Phase 2 — after this, "staff can view the calendar grid and create a walk-in booking that atomically, safely decrements inventory" (ROADMAP.md's Phase 2 goal, verbatim) is fully true, not just true at the API level.

## Output
A booking form on the Dashboard (below the calendar grid) that calls the real `POST /api/bookings`, shows success (with the real total charged) or a clear error, and triggers the calendar grid to re-fetch so staff see the updated availability immediately without a manual page refresh.
</objective>

<acceptance_criteria>

## AC-1: Staff can create a valid walk-in booking from the browser
```gherkin
Given an authenticated FRONT_DESK/HOTEL_ADMIN/SUPER_ADMIN user with a room type and rate plan selected
When they fill the booking form (dates, quantity, guest name) and submit
Then POST /api/bookings is called with the correct real values, a success confirmation shows the real totalAmount from the response, and the calendar grid re-fetches to show reduced availability for the booked dates
```

## AC-2: Every real backend error is shown clearly, not silently swallowed or shown as raw JSON
```gherkin
Given a submission that the backend rejects (400 invalid input, 403 wrong role, 404 cross-tenant/nonexistent, 409 sold-out/duplicate/pricing-unavailable, 500 unexpected)
When the response returns
Then the form shows a clear, specific message reflecting what actually happened — not a generic catch-all for every case, and never raw JSON or a stack trace
```

## AC-3: Network failure is handled distinctly from a rejected request
```gherkin
Given the backend is unreachable during submission
When the form is submitted
Then a distinct "unable to reach the server" message is shown — not confused with a validation/rejection error, and the form does not hang or crash
```

## AC-4: Double-submission is guarded client-side too
```gherkin
Given a submission is already in flight
When the user clicks Submit again (or double-clicks)
Then the button is disabled while in flight — no second request is fired from the same click sequence, complementing (not replacing) the backend's own 30-second dedupe guard from 02-03
```

## AC-5: Calendar grid reflects the new booking without a manual refresh
```gherkin
Given a successful booking submission for the currently-viewed room type/week
When the booking completes
Then the calendar grid automatically re-fetches and shows the reduced availability for the booked dates — staff never have to manually reload the page to see the effect of the booking they just made
```

## AC-6: Booking form is not offered to roles the backend would reject
```gherkin
Given a user with the HOUSEKEEPING role (which 02-03's backend already rejects with 403)
When they view the Dashboard
Then the booking form is not shown (a UX courtesy, not a security control — the backend's role gate from 02-03 remains the actual enforcement point regardless of what the frontend shows or hides)
```
