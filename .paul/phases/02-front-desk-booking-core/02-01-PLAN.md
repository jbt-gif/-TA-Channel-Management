<objective>
## Goal
Build the front-desk authentication layer: password hashing, a login endpoint that issues a JWT, and an auth middleware that every later Phase 2+ route uses to know which hotel a request belongs to.

## Purpose
ROADMAP.md's Phase 2 scope (calendar grid API, booking transaction, UI) never named authentication, but every one of those endpoints needs an authenticated hotelId to scope its queries — the entire multi-tenant isolation pattern built in Phase 1 is inert without a way to know who's asking. This is also the "multi-tenant auth/isolation phase" SPECIAL-FLOWS.md reserves a security-review pass for, so it gets built and reviewed as its own unit, not folded silently into the calendar API.

## Output
A working POST /api/auth/login endpoint, a reusable auth middleware other routes will import, a small admin-run script for onboarding staff accounts (matches the white-glove onboarding model — no self-service signup), and a smoke test proving login, rejection, and middleware enforcement all work against real data.
</objective>

<acceptance_criteria>

## AC-1: Staff can log in with valid credentials
```gherkin
Given a User row exists with a real bcrypt passwordHash (created via the admin create-user script)
When POST /api/auth/login is called with that user's correct email/password
Then the response is 200 with a JWT containing userId, hotelId, and role
```

## AC-2: Invalid credentials are rejected without leaking which part was wrong
```gherkin
Given a User row exists
When POST /api/auth/login is called with a wrong password, or an email that doesn't exist
Then the response is 401 with a generic "invalid credentials" message in both cases — never revealing whether the email existed
```

## AC-3: Auth middleware enforces a valid, unexpired token on protected routes
```gherkin
Given a protected test route wrapped with the auth middleware
When a request is made with no Authorization header, a malformed token, or a token signed with the wrong secret
Then the response is 401 and the route handler never executes
```

## AC-4: Auth middleware correctly attaches hotel-scoping context
```gherkin
Given a valid JWT for a FRONT_DESK user belonging to Hotel A
When a request hits a protected route with that token
Then req.auth contains { userId, hotelId: <Hotel A's id>, role: FRONT_DESK } — the exact shape every future Phase 2+ route will rely on for tenant scoping
```

## AC-5: Passwords are never stored or logged in plaintext
```gherkin
Given the create-user script is run with a plaintext password argument
When the resulting User row is inspected
Then passwordHash contains a bcrypt hash, never the original plaintext, and no plaintext password appears in any script output or log line
```

<task type="auto">
  <name>Task 2: Build the login endpoint and auth middleware</name>
  <files>package.json, .env.example, src/lib/auth.ts, src/middleware/auth.ts, src/routes/auth.ts, src/server.ts</files>
  <action>
    Add `jose` as a dependency (JWT signing/verification — chosen over jsonwebtoken for native ESM support, matching this project's ESM setup from 01-01).

    Add `JWT_SECRET` to .env.example (a placeholder value, real value goes in .env which is gitignored) — generate and set a real random 32+ byte secret in .env directly (do not print it to chat or commit it).

    <!-- audit-added --> Also add `express-rate-limit` as a dependency — brute-force protection for the login endpoint. bcrypt cost 12 alone is not a throttle (~100-300ms per guess is still several guesses/sec unthrottled); this system guards guest PII and payment records behind these credentials.

    In src/lib/auth.ts:
    - `signToken({ userId, hotelId, role }): Promise<string>` — HS256 JWT via jose, 12-hour expiry (matches a staff shift/workday; no refresh-token flow in this plan, staff re-authenticate daily)
    - `verifyToken(token: string): Promise<{ userId, hotelId, role }>` — throws on invalid signature, expiry, or malformed token
    <!-- audit-added --> - At module load, validate `process.env.JWT_SECRET` exists AND is at least 32 characters — `process.exit(1)` with a clear error if not. A short or missing secret is forgeable; failing loudly at startup is the correct behavior, not a inconvenience to work around.

    In src/routes/auth.ts:
    - Apply an `express-rate-limit` limiter to POST /api/auth/login: <!-- audit-added --> max 5 attempts per 15 minutes per IP, returning 429 on exceed (in-memory store — appropriate for the current single-instance Railway/Render deployment; revisit with a shared store like Redis only if the backend is horizontally scaled, tracked as a deferred item, not built now)
    - POST /api/auth/login — accepts { email, password }. <!-- audit-added --> Normalize email to lowercase before lookup, matching create-user.ts's normalization. Look up User by email (deletedAt: null). If not found OR bcrypt.compare fails, return 401 with the exact same generic message either way (prevents user-enumeration via response difference — do not return different messages or status codes for "no such email" vs "wrong password"). <!-- audit-added --> Log failed attempts to console as a single structured line (timestamp, normalized email, source IP — never the password) — this project has no dedicated audit-log table yet (that's Phase 7's monitoring work), but a login endpoint producing zero trace of failed attempts fails a basic post-incident-reconstruction bar even before that phase exists. On success, call signToken and return { token }.
    <!-- audit-added --> - Wrap the User lookup and bcrypt compare in try/catch. On any unexpected error (e.g. DB unreachable), log the real error server-side and return a generic 500 with no error detail, stack trace, or internals in the response body.

    In src/middleware/auth.ts:
    - Express middleware reading `Authorization: Bearer <token>`, calling verifyToken, attaching `req.auth = { userId, hotelId, role }` on success, or responding 401 immediately (not calling next()) on any failure — no route handler should ever run without a verified token when this middleware is applied. <!-- audit-added --> Wrap verifyToken in try/catch — any error (including unexpected ones, not just expected JWT-invalid errors) must result in a 401 with a generic message, never a 500 or a leaked error detail.

    Wire the login route into src/server.ts. Do NOT apply the auth middleware to the login route itself or the existing /health route — those are correctly unauthenticated.

    Avoid: storing the JWT secret anywhere but .env; logging tokens or passwords at any point; a shared/default JWT_SECRET fallback if the env var is missing (fail startup loudly instead — a silent fallback secret is a real vulnerability, not a convenience).
  </action>

## SCOPE LIMITS
- No self-service signup/registration endpoint — matches PROJECT.md's white-glove onboarding constraint; staff accounts are created via the admin script only
- No refresh-token flow, no password-reset flow, no "remember me" — 12-hour JWT expiry, daily re-login, is the full scope of this plan
- <!-- audit-added --> **Accepted risk, on the record:** the JWT-stateless approach (chosen over server-side sessions specifically for simplicity) means a token cannot be instantly revoked before its 12-hour expiry — a stolen front-desk terminal or a same-day-terminated employee retains a working token until it naturally expires. This is a deliberate, known tradeoff of the chosen architecture, not an oversight. If this residual risk becomes unacceptable later (e.g. after a real incident, or once multiple properties are live), the mitigation is a session-based revocation list or moving to server-side sessions — not silently patched in without a decision.
- No CORS configuration — no cross-origin browser client exists yet; add it in whichever plan first stands up a frontend calling this API from a different origin
- No distributed/shared rate-limit store (e.g. Redis) — the in-memory limiter added in Task 2 is correct for the current single-backend-instance deployment; revisit only if horizontally scaled
- No persistent audit-log table for auth events — Task 2's console logging of failed attempts is the minimal trace for now; a real structured audit log belongs to Phase 7's monitoring/observability work
- No calendar grid API, no booking transaction, no UI — those are 02-02/02-03/02-04, this plan only builds the auth foundation they depend on
- No HOTEL_ADMIN-only or SUPER_ADMIN-only route restrictions yet — role is attached to req.auth for later routes to check, but no role-based authorization logic is built in this plan
