<objective>
## Goal
Staff can create a walk-in booking spanning one or more nights that atomically, safely decrements inventory — no two concurrent requests can oversell the same room-type/date, even when racing for the last available room.

## Purpose
This is the actual write-path backstop for the project's Core Value ("prevents overbookings"). Phase 1's DB-level CHECK constraint (`bookedCount + heldCount <= availableCount`) is the last line of defense; this plan is the first — the transaction logic that's supposed to make the CHECK constraint never actually fire under normal operation. ROADMAP.md flags this as the highest-risk piece of Phase 2, needing deliberate transaction/locking design rather than a naive create.

## Output
`POST /api/bookings` — authenticated, hotel-scoped endpoint. Guest find-or-create, Booking + BookingItem creation, and per-date DailyInventory decrement all inside one atomic transaction. Two smoke tests: functional correctness (happy path, validation, cross-tenant isolation) and a live concurrency test (50 simultaneous requests for one remaining room).
</objective>

<acceptance_criteria>

## AC-1: Staff can create a valid walk-in booking
```gherkin
Given an authenticated front-desk user and an available room type/rate plan for a 2-night date range
When they POST /api/bookings with roomTypeId, ratePlanId, checkInDate, checkOutDate, quantity, and guest info
Then the response is 201 with the created booking, totalAmount computed from the real per-night RatePlanDailyRate values (not a flat rate x nights), and DailyInventory.bookedCount incremented by quantity for every date in range
```

## AC-2: Booking creation is hotel-scoped
```gherkin
Given an authenticated user for Hotel A
When they POST /api/bookings targeting a roomTypeId belonging to Hotel B, or a genuinely nonexistent roomTypeId
Then both requests return byte-identical 404 responses — never 403, never a response that lets an attacker distinguish "exists but not yours" from "doesn't exist"
```

## AC-3: Concurrent requests cannot oversell the last room
```gherkin
Given a room type with exactly 1 available room for a given date
When 50 concurrent POST /api/bookings requests target that same room/date simultaneously
Then exactly 1 request succeeds (201) and 49 receive a clean 409 (not 500, not a hang), and a direct DB query afterward confirms bookedCount + heldCount <= availableCount held throughout
```

## AC-4: Multi-night bookings are all-or-nothing
```gherkin
Given a 3-night booking request where night 2 has zero availability but nights 1 and 3 do
When the booking is submitted
Then the entire request is rejected with 409, and DailyInventory.bookedCount is unchanged for nights 1 and 3 — no partial decrement left behind
```

## AC-5: Invalid input rejected before any DB mutation
```gherkin
Given a request with missing required fields, checkOutDate <= checkInDate, a past checkInDate, a stay exceeding the maximum allowed length (30 nights), or a roomTypeId/ratePlanId pair that don't belong to the same hotel
When submitted
Then the response is 400 and no Guest, Booking, BookingItem, or DailyInventory row is created or modified
```

## AC-6: Endpoint requires authentication
```gherkin
Given no Authorization header or an invalid/expired token
When POST /api/bookings is called
Then the response is 401
```

## AC-7: Only front-desk-capable roles can create bookings
```gherkin
Given an authenticated user with role HOUSEKEEPING
When they POST /api/bookings
Then the response is 403 — booking creation is limited to FRONT_DESK, HOTEL_ADMIN, and SUPER_ADMIN
```

## AC-8: Rapid duplicate submission does not create two bookings
```gherkin
Given a staff member submits the exact same booking request twice within a short window (e.g. double-click, or a network retry after a slow response)
When the second request arrives
Then it is rejected (409, duplicate) rather than creating a second Booking for the same guest/room/date-range — no two Bookings for the same hotelId+roomTypeId+checkInDate+checkOutDate+guest email exist within the dedupe window
```

<!-- audit-added -->
## AC-9: Missing pricing data is a hard stop, not a silent gap
```gherkin
Given a booking request whose date range includes at least one date with no RatePlanDailyRate row for the requested rate plan
When submitted
Then the response is 409 (pricing unavailable for requested dates) and no Guest, Booking, BookingItem, or DailyInventory row is created — the total is never silently computed from a partial date range
```

  <name>Task 1: POST /api/bookings — atomic booking creation endpoint</name>
  <files>src/routes/bookings.ts, src/app.ts</files>
  <action>
    Create `bookingsRouter` mounted at `/api/bookings`, protected by `requireAuth`.

    <!-- audit-added: AC-7 role gate -->
    Role gate (before any other logic): reject with 403 unless `req.auth.role` is one of `FRONT_DESK`, `HOTEL_ADMIN`, `SUPER_ADMIN`. `HOUSEKEEPING` must never be able to create bookings.

    Request body: { roomTypeId, ratePlanId, checkInDate, checkOutDate (YYYY-MM-DD strings), quantity, guest: { firstName, lastName, email?, phone? } }.

    Validation (before any DB write, return 400 on failure):
    - All required fields present, quantity is a positive integer
    - Round-trip date validation on both dates (same technique as 02-02's calendar endpoint — reformat parsed Date, compare to original string, rejects impossible dates like 2026-02-30)
    - checkOutDate strictly after checkInDate
    - checkInDate is not in the past (Asia/Manila date, matching the project's existing timezone convention)
    - <!-- audit-added: AC-5 max-nights --> Stay length (nights between checkInDate and checkOutDate) does not exceed 30 — reject with 400 otherwise. Bounds the transaction to a sane number of per-date statements, matching 02-02's precedent of capping range size (>400-day rejection).

    Ownership check: fetch RoomType and RatePlan, confirm both exist AND both belong to req.auth.hotelId AND ratePlan.roomTypeId matches roomTypeId (if that relation exists) — on any failure, return the exact same 404 body used for the "genuinely doesn't exist" case (copy the byte-identical-404 pattern from src/routes/roomTypes.ts). Wrap this check inside the same try/catch as everything else, not before it.

    <!-- audit-added: AC-9 missing-rate guard -->
    Pricing-availability check (after ownership check, before the transaction): fetch all `RatePlanDailyRate` rows for this ratePlanId across every date in [checkInDate, checkOutDate). If the returned row count is less than the number of nights, return 409 ("pricing unavailable for requested dates") — never proceed to compute a total from a partial set of dates.

    <!-- audit-added: AC-8 duplicate-submission guard -->
    Duplicate-submission check (same transaction, first step): before creating anything, query for an existing Booking with the same hotelId, roomTypeId (via bookingItems), checkInDate, checkOutDate, and guest email, created within the last 30 seconds. If found, return 409 ("duplicate submission") instead of creating a second Booking. This is a lightweight dedupe, not a full idempotency-key system — sufficient for a front-desk double-click or a client retry, not intended to survive a client deliberately reordering fields.

    Core transaction — wrap in `prisma.$transaction(async (tx) => { ... })`:
    1. For each date in [checkInDate, checkOutDate): run the conditional update via `tx.$executeRaw` using a **Prisma tagged-template literal** (e.g. `` tx.$executeRaw`UPDATE "DailyInventory" SET "bookedCount" = "bookedCount" + ${quantity} WHERE "hotelId" = ${hotelId} AND "roomTypeId" = ${roomTypeId} AND date = ${date} AND "bookedCount" + "heldCount" + ${quantity} <= "availableCount"` `` — the tagged-template form auto-parameterizes every `${...}` interpolation. <!-- audit-added --> **Do not build this SQL via string concatenation or `Prisma.raw`/`.sql` string interpolation** — that would reopen a SQL-injection path on a financial write endpoint even though current inputs are server-validated. Capture the returned affected-row count.
    2. If any date's affected count !== 1, throw an Error (e.g. `SOLD_OUT`) inside the transaction — Prisma rolls back everything already applied in this transaction automatically, so earlier dates' increments in this same booking attempt are undone. This is what makes AC-4 (all-or-nothing) hold.
    3. Find-or-create Guest: if `guest.email` provided, `tx.guest.findFirst({ where: { hotelId, email } })`, else always create new. Never fuzzy-match by name.
    4. Compute totalPriceSnapshot: sum `RatePlanDailyRate.rate` (read the real field name from schema.prisma) for every date in range for this ratePlanId, multiplied by quantity. <!-- audit-added --> **Use Prisma's `Decimal` arithmetic (decimal.js `.plus()`/`.times()`), never convert to native JS `number` for the running sum** — this is a financial total on a record the project's own decision log already treats as audit-critical; float summation risks silent cent-level drift. Do NOT use a flat per-night rate x nights — rates vary per date, per the project's existing decision log (PROJECT.md's "Price/total snapshots" decision).
    5. Create Booking (status: CONFIRMED, source: WALK_IN, hotelId, guestId, createdByUserId: req.auth.userId, totalAmount: the computed total) and one BookingItem (hotelId, bookingId, roomTypeId, ratePlanId, checkInDate, checkOutDate, quantity, totalPriceSnapshot: the same computed total).

    On transaction success: return 201 with the created booking (including bookingItems).
    On `SOLD_OUT` error specifically: return 409 with a clean message, not a stack trace.
    On any other unexpected error: return 500 with no leaked detail, matching the try/catch discipline from 02-01/02-02 (entire handler body, including the role gate and ownership check, inside one try/catch).

    Avoid: computing the date-range total by multiplying one sampled rate by night count (silently wrong when rates vary); performing the availability check as a separate SELECT before the UPDATE (that's exactly the race condition this plan exists to prevent — the check and the increment must be the same atomic statement); string-concatenated raw SQL (SQL injection); native-float money arithmetic (precision drift).
  </action>
  <verify>Manual curl: POST valid booking returns 201 with correct totalAmount matching manually-summed RatePlanDailyRate values; POST with cross-tenant roomTypeId returns byte-identical 404 to a nonexistent id; POST with checkOutDate before checkInDate returns 400; POST as HOUSEKEEPING role returns 403; POST twice rapidly with identical body returns 201 then 409; POST for a date range with a gap in RatePlanDailyRate returns 409; POST for a 45-night stay returns 400.</verify>

<assumptions_requiring_review>

## Assumption 1: Booking status set directly to CONFIRMED, not PENDING_PAYMENT
**What's assumed:** Despite `Booking.status` defaulting to `PENDING_PAYMENT` in the schema, this plan sets it to `CONFIRMED` immediately on creation.
**Alternative not chosen:** Leave the schema default (`PENDING_PAYMENT`) and add a manual staff "confirm" step.
**Why conservative-leaning, not just convenient:** No online payment flow exists until Phase 5 — PROJECT.md scopes this phase as "front-desk manual booking + walk-in logging," implying staff are directly confirming reservations in person. Reversible later with a one-value status change if you'd rather walk-ins start as pending.
**Ask:** Does a walk-in booking count as confirmed the moment staff creates it, or should it require a separate confirm action?

## Assumption 2: No Payment record created in this plan
**What's assumed:** `totalAmount` is computed and stored on Booking, but nothing tracks whether/how the guest actually paid — no Payment row, no cash-received flag.
**Alternative not chosen:** Create a Payment row with method left null/TBD, or add a `paidInCash: boolean` field.
**Why flagged, not just noted:** This is the exact "financial ambiguity" category worth your explicit sign-off on, even though no real money moves through the system yet (Xendit isn't wired in until Phase 5). Low risk today, but silently deferring it means there's currently no record at all of a walk-in guest having paid.
**Ask:** Acceptable to leave payment-tracking fully absent until Phase 5, or do you want a minimal placeholder now?

## Assumption 3: Guest matching is exact-email-only, never fuzzy
**What's assumed:** Find-or-create by exact `(hotelId, email)` match if email is given; otherwise always create a new Guest row, even if name matches an existing guest.
**Why conservative:** Guessing identity matches on name alone risks merging two different people; occasional duplicate Guest rows are harmless and can be merged manually later. Not raising this as a hard question — stating it so it's visible, not silent.

## Assumption 4: `quantity` correctly gates on rooms-available, not just "any availability"
**What's assumed:** The conditional UPDATE checks `bookedCount + heldCount + quantity <= availableCount`, so a request for quantity=3 correctly fails if only 2 rooms remain, rather than succeeding and overselling by 1.
**Why noted:** This is load-bearing for AC-3/AC-4 and easy to get subtly wrong (e.g. checking `quantity <= availableCount - bookedCount` without also accounting for `heldCount`). Flagged so it's checked explicitly during verification, not just assumed correct because the query looks right.

</assumptions_requiring_review>
