<objective>
## Goal
Build the read-only calendar grid query API: list a hotel's room types, and fetch the DailyInventory + per-rate-plan RatePlanDailyRate grid for a room type over a date range — with query-level tenant isolation enforced, not just documented.

## Purpose
This is the first plan that actually queries hotel-scoped data using an authenticated request (02-01 only built the auth layer, no protected business-data route existed yet). It's also the "multi-tenant isolation" half of the auth/isolation risk class SPECIAL-FLOWS.md reserves security-review for — a bug here means one hotel's front desk could see another hotel's occupancy, rates, or room counts. That's a direct violation of the multi-tenant guarantee the whole product is sold on.

## Output
Two protected endpoints (room-type list, calendar grid), proven via smoke test to return correct data for the authenticated hotel and to refuse cross-tenant access — not by trusting the query filter alone, but by verifying a same-shaped request against a different hotel's data actually fails.
</objective>

<acceptance_criteria>

## AC-1: Authenticated user can list their hotel's room types
```gherkin
Given a FRONT_DESK user authenticated for Hotel A
When GET /api/room-types is called with a valid token
Then the response is 200 with Hotel A's active RoomTypes, each including its active RatePlans
```

## AC-2: Room-type list never leaks another hotel's data
```gherkin
Given Hotel A and Hotel B both have RoomTypes in the database
When a Hotel A user calls GET /api/room-types
Then only Hotel A's RoomTypes appear in the response — verified by asserting Hotel B's RoomType id is absent, not just that the count looks right
```

## AC-3: Calendar grid returns correct data for the authenticated hotel
```gherkin
Given a RoomType under Hotel A with seeded DailyInventory and RatePlanDailyRate rows
When GET /api/room-types/:roomTypeId/calendar?startDate=X&endDate=Y is called by a Hotel A user for that RoomType
Then the response includes exactly one entry per calendar date in range — including dates with no DailyInventory row, marked seeded:false rather than omitted — with availableCount/bookedCount/heldCount/isClosed and each active RatePlan's price/minStay for seeded dates
```

## AC-4: Cross-tenant roomTypeId access is refused, not just filtered
```gherkin
Given a RoomType belongs to Hotel B
When a Hotel A user requests GET /api/room-types/:hotelBRoomTypeId/calendar
Then the response is 404 (not 403) — a 403 would confirm the id exists at all, which itself leaks information across tenants
```

## AC-5: Both endpoints require authentication
```gherkin
Given no Authorization header, or an invalid one
When either GET /api/room-types or GET /api/room-types/:id/calendar is called
Then the response is 401 and no query against RoomType/DailyInventory/RatePlanDailyRate ever runs
```

## AC-6: Invalid date ranges are rejected before any database query runs
```gherkin
Given the calendar endpoint is called with a missing startDate/endDate, a malformed date string, a syntactically-valid-but-impossible date (e.g. 2026-02-30), endDate before startDate, or a range exceeding 400 days
Then the response is 400 with a clear error message, and no DailyInventory/RatePlanDailyRate query executes
```

<task type="auto">
  <name>Task 2: Calendar grid endpoint with tenant-ownership check and date validation</name>
  <files>src/routes/roomTypes.ts</files>
  <action>
    Add to src/routes/roomTypes.ts:

    - `GET /:roomTypeId/calendar` (mounted under `/api/room-types`), wrapped with `requireAuth`:

      1. **Validate query params first, before any database query:** `startDate` and `endDate` must both be present and match `/^\d{4}-\d{2}-\d{2}$/`. Parse both as UTC-midnight Dates (matching how `@db.Date` columns are stored — no timezone offset math needed here, unlike the Phase 1 seed worker, because these are explicit client-supplied calendar dates, not a "today" computation). <!-- audit-added --> After parsing, verify the round trip: reformat the parsed Date back to `YYYY-MM-DD` and confirm it matches the original input string exactly. This rejects syntactically-valid-but-impossible dates like `2026-02-30`, which JS's lenient `Date` parsing would otherwise silently roll over to March 2nd instead of erroring — a fat-fingered date picker input should produce a clear 400, not a silently wrong range. Reject with 400 if: either is missing/malformed, fails the round-trip check, `endDate < startDate`, or the span exceeds 400 days (`(endDate - startDate) / 86400000 > 400`). Return a clear error message identifying which check failed.

      <!-- audit-added: entire handler body from here through the response must be inside one try/catch, not just the data-query steps --> Wrap everything from step 2 onward in a single try/catch matching 02-01's pattern — generic 500 on any unexpected failure (including a transient error from the ownership-check query itself in step 2, not only the later grid queries), no leaked detail. The original draft of this task only wrapped the data-query steps, leaving the ownership check outside error handling — fixed here so a DB hiccup during step 2 can't produce an uncontrolled Express error response instead of the established generic-500 pattern.

      2. **Verify tenant ownership before returning any data:** `prisma.roomType.findFirst({ where: { id: roomTypeId, hotelId: req.auth.hotelId, deletedAt: null } })`. If null — whether because the roomTypeId doesn't exist at all, or because it belongs to a different hotel — return 404 with a generic "Room type not found" message. Do NOT distinguish "doesn't exist" from "belongs to another hotel" in the response; that distinction is itself a tenant-isolation leak (see AC-4).

      3. **Query the grid data**, scoped to the now-verified roomTypeId:
         - `DailyInventory` rows for `roomTypeId` within `[startDate, endDate]`, ordered by date.
         - Active `RatePlan`s for this roomType, then their `RatePlanDailyRate` rows within the same range.
         - <!-- audit-added --> Build `days[]` by iterating every calendar date in `[startDate, endDate]` explicitly (not by mapping over whatever DailyInventory rows happen to exist) — for each date, look up the matching DailyInventory row if present. If no row exists for a date (a normal state: a RoomType can exist before its 365-day seed has run, per 01-02's own zero-Rooms/zero-RoomType-yet-seeded precedent), emit that day with `seeded: false` and `availableCount`/`bookedCount`/`heldCount`/`isClosed` all `null`, rather than silently omitting the date from the array. A `days[]` array shorter than the requested range with no explanation is a data-completeness bug, not an acceptable gap — the frontend needs to distinguish "not seeded yet" from "seeded, zero availability."
         - Assemble into: `{ roomType: {id, name, baseCapacity}, ratePlans: [{id, name, isRefundable, includesBreakfast}], days: [{ date, seeded, availableCount, bookedCount, heldCount, isClosed, rates: { [ratePlanId]: { price, minStay } } }] }`. A date with no RatePlanDailyRate row for a given ratePlan simply omits that ratePlanId from `rates` for that day (can happen if seeding hasn't run for a newly-created rate plan) — do not error on this, the frontend (02-04) will handle a missing rate as "not yet priced."
  </action>
