<objective>
## Goal
Front-desk staff can see a real 14-day availability/rate grid for a chosen room type — the actual ARI (availability/rate/inventory) view PROJECT.md's Core Value promises, replacing 02-04's placeholder Dashboard with real data from the already-live calendar API.

## Purpose
02-02 built the calendar query API; 02-03 built the overbooking-safe write path. Neither is visible to a human yet. This plan is the first place a front-desk user can actually see whether a room is available before deciding to book it — the direct visual precondition for 02-06's booking form.

## Output
The Dashboard route now shows: a room-type selector, a 14-day grid with Prev/Next week navigation, per-date availability status, and per-rate-plan pricing — all sourced live from `GET /api/room-types` and `GET /api/room-types/:id/calendar`.
</objective>

<acceptance_criteria>

## AC-1: Room-type selector populated from real data
```gherkin
Given an authenticated front-desk user with at least one room type at their hotel
When the Dashboard loads
Then a dropdown/selector lists all of that hotel's real room types (from GET /api/room-types), with the first one selected by default
```

## AC-2: Grid shows real availability and pricing
```gherkin
Given a room type with seeded DailyInventory and RatePlanDailyRate data
When it's selected in the grid
Then each of the 14 displayed dates shows the correct available-room count (availableCount - bookedCount - heldCount) and each rate plan's correct per-date price, matching what GET /api/room-types/:id/calendar actually returns — not a placeholder or a value computed independently on the frontend
```

## AC-3: Unseeded dates are visually distinct, never silently shown as available
```gherkin
Given a date beyond the hotel's seeded horizon (seeded: false in the API response)
When it appears in the grid
Then it is rendered with a clear "not yet available" / unseeded indicator — never blank, never styled identically to a genuinely available date
```

## AC-4: Switching room type or week re-fetches correctly
```gherkin
Given the grid is showing room type A, week of [date range]
When the user selects room type B, or clicks Next/Prev week
Then the grid re-fetches and displays B's (or the new week's) real data — no stale data from the previous selection lingers, and a loading state is shown during the fetch
```

## AC-5: Zero-room-types empty state
```gherkin
Given a hotel with no room types configured yet
When the Dashboard loads
Then a clear "no room types configured yet" message is shown — not a crash, not an empty selector with a broken grid underneath
```

## AC-6: Sold-out dates are visually distinct
```gherkin
Given a date where available-room count is 0 (availableCount - bookedCount - heldCount <= 0) or isClosed is true
When it appears in the grid
Then it is visually distinguishable from an available date (e.g. different background/label) — this is the actual overbooking-prevention value made visible to staff, not cosmetic polish
```

  <action>
    Create typed wrapper functions around `apiFetch` (from `../lib/api`), matching the REAL response shapes in `src/routes/roomTypes.ts` exactly — read that file, do not assume field names.

    `fetchRoomTypes(): Promise<RoomType[]>` — calls `GET /room-types`. Type: `{ id: string; name: string; baseCapacity: number; ratePlans: { id: string; name: string; isRefundable: boolean; includesBreakfast: boolean }[] }[]`.

    `fetchCalendar(roomTypeId: string, startDate: string, endDate: string): Promise<CalendarResponse>` — calls `GET /room-types/${roomTypeId}/calendar?startDate=${startDate}&endDate=${endDate}`. Type matches the real response: `{ roomType: {...}, ratePlans: [...], days: { date: string; seeded: boolean; availableCount: number | null; bookedCount: number | null; heldCount: number | null; isClosed: boolean | null; rates: Record<string, { price: string; minStay: number }> }[] }`. Throw a clear error if the response is a 404 (cross-tenant/nonexistent — shouldn't normally happen from this UI since roomTypeId always comes from `fetchRoomTypes()`'s own results, but don't silently swallow it if it does).

    Avoid: duplicating apiFetch's token/401 logic here — this file only shapes requests/responses, `apiFetch` already handles auth.
  </action>

<task type="auto">
  <name>Task 2: CalendarGrid component + Dashboard wiring</name>
  <files>frontend/src/components/CalendarGrid.tsx, frontend/src/pages/Dashboard.tsx</files>
  <action>
    `CalendarGrid.tsx`: presentational component taking a `CalendarResponse` (from Task 1) as props. Renders a table: columns = the 14 dates, rows = one per rate plan (price for that date) plus a top "Availability" row (available count = availableCount - bookedCount - heldCount, or "—" if the date isn't seeded).

    Per-cell rendering rules (these are the actual audit-relevant logic, not styling detail):
    - `seeded: false` → distinct "not yet available" cell state (e.g. muted/hatched), never rendered the same as a real 0-available cell
    - `isClosed: true` OR computed available count `<= 0` → distinct "sold out / closed" state, visually different from both "available" and "unseeded"
    - <!-- audit-added --> A seeded date where `rates[ratePlanId]` is `undefined` (a rate plan with no `RatePlanDailyRate` row for that specific date — e.g. a rate plan created after some dates were already seeded) → render that cell as "no rate set," never crash on `undefined.price` and never silently render a blank cell that could be misread as free/zero-cost
    - Otherwise → show the real available count and, per rate plan row, the real price. <!-- audit-added --> `price` arrives as a string (JSON-serialized Prisma Decimal) — parse with `Number(price)` and format with `Intl.NumberFormat('en-PH', { style: 'currency', currency: 'PHP' })`, not ad hoc string concatenation, to avoid silently mis-rendering a value like `"3500.00"` as `"₱3500.00"` with inconsistent grouping/decimals.

    `Dashboard.tsx`: replace the placeholder content (keep the existing user-info header + logout button from 02-04). Add:
    - Room-type selector (`<select>`, populated via `fetchRoomTypes()` on mount). <!-- audit-added --> Track loading state for this fetch separately from "confirmed zero room types" — while the fetch is in flight, show a loading state, not AC-5's empty-state message; only render the empty state once the fetch has actually resolved with zero results (same isLoading-gate discipline as 02-04's AuthContext, applied here to avoid a misleading flash of "no room types configured" before data arrives). If the list is empty after loading, render AC-5's empty state and stop, don't attempt a calendar fetch.
    - <!-- audit-added --> `startDate` computed via an explicit Asia/Manila UTC-midnight helper — reuse the exact `+8h offset, then UTC-midnight` pattern already established in `src/lib/seed-inventory.ts`'s `getManilaToday()` (mirror it client-side; do not use `new Date().toISOString().slice(0,10)` or any browser-local-timezone-dependent computation, since a staff member's machine clock/timezone isn't guaranteed to be Asia/Manila and the backend's own date semantics are Manila-anchored, not local-machine-anchored). `endDate = startDate + 13 days`.
    - Prev/Next week buttons shifting `startDate` by ±7 days, re-fetching on change
    - Loading state shown while `fetchCalendar` is in flight (AC-4); error state (network failure, matching Task 1's error handling) shown distinctly from "loading" and from "no data"
    - Re-fetch whenever `selectedRoomTypeId` or `startDate` changes
    - <!-- audit-added --> Guard against out-of-order responses: if the user clicks Next/Prev or switches room type again before the current `fetchCalendar` call resolves, the earlier in-flight request's response must not overwrite the grid once a newer request has since been fired. Implement with an `AbortController` (abort the previous request when a new one starts) or a simple "latest request id" ref compared against on resolution — without this, rapid clicking can leave the grid showing stale data for the wrong week/room type with no visual indication anything is wrong.

    Avoid: fetching calendar data before a room type is selected (wasted request, and would 404 or error against an undefined id); recomputing prices/availability on the frontend independently of what the API returned — always render the API's own numbers, never re-derive them client-side (that's exactly the kind of drift that could silently show incorrect availability to staff).
  </action>
