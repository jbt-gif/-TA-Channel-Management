<task type="auto">
  <name>Task 2: API client + AuthContext + ProtectedRoute</name>
  <files>frontend/src/lib/api.ts, frontend/src/context/AuthContext.tsx, frontend/src/routes/ProtectedRoute.tsx</files>
  <action>
    `src/lib/api.ts`: a thin fetch wrapper. Base URL from `import.meta.env.VITE_API_URL ?? "/api"`. Export a function that attaches `Authorization: Bearer {token}` when a token is present, and — critically — on receiving a 401 from ANY authenticated call, clears the stored token and triggers a redirect to `/login` (this is what makes AC-5 hold; don't just leave 401-handling to individual call sites, centralize it in the client).

    `src/context/AuthContext.tsx`: React Context holding `{ token, userId, hotelId, role } | null` plus `login(email, password)` and `logout()`. `login()` POSTs to `/api/auth/login`, stores the returned token in `localStorage` (documented tradeoff: localStorage is XSS-exposed but matches this project's existing stateless-Bearer-token backend design — no httpOnly-cookie support exists on the backend, and adding one is out of scope/would violate this plan's boundaries below). On mount, if a token exists in localStorage, call `GET /api/me` to validate it and populate `userId`/`hotelId`/`role` — if that call 401s, clear the token (AC-5).

    `src/routes/ProtectedRoute.tsx`: wrapper component — if `AuthContext`'s token is null, redirect to `/login` (React Router `<Navigate>`); otherwise render children (AC-4).

    <!-- audit-added -->
    `AuthContext` must expose an explicit `isLoading` boolean (true while the mount-time `GET /api/me` validation is in flight). `ProtectedRoute` must not make its redirect decision until `isLoading` is false — otherwise a user with a genuinely valid stored token gets incorrectly bounced to `/login` during the async validation window, a real correctness bug in AC-4/AC-5, not just a UI flicker.

    Avoid: storing the JWT in a plain top-level global variable (lost on refresh) or in sessionStorage without documenting why (localStorage is the deliberate choice here — front-desk staff need the session to survive a browser refresh during a shift).
  </action>
  <verify>Manual: with dev server running and no valid token, navigating to /dashboard redirects to /login (confirms ProtectedRoute + AC-4 before Task 3's login page even exists, using a temporary hardcoded test route if needed)</verify>
  <done>AC-4, AC-5 satisfied</done>
</task>

    Error handling — two distinct failure modes, handled differently:
    1. **401 from the backend (wrong credentials):** Display the exact generic message the backend returns (or a fixed string like "Invalid email or password" if you prefer not to render server text directly) — <!-- audit-added --> **never construct a different message based on response inspection** (e.g. never show "no account with that email" vs "wrong password" as separate messages). The backend deliberately returns byte-identical 401 bodies for both cases specifically to prevent email-enumeration (verified in 02-01's SECURITY.md, 10/10 mitigations) — a frontend that infers and displays a more "helpful" distinction would silently reopen that exact vulnerability at the UI layer.
    2. <!-- audit-added --> **Network-level failure (fetch throws — backend unreachable, DNS failure, etc.):** Catch this separately from the 401 case and show a distinct generic message (e.g. "Unable to reach the server, please try again") — do not let an unhandled promise rejection produce a blank page or uncaught error.

    Avoid: rendering the raw fetch Response body/JSON directly into the DOM under any circumstances (defense-in-depth even though the backend's error bodies are already safe, non-HTML JSON).

<boundaries>

## DO NOT CHANGE
- src/routes/auth.ts, src/middleware/auth.ts, src/lib/auth.ts — backend auth is stable and already security-verified (02-01); this plan is a pure consumer, not a modifier, of that contract
- No backend changes of any kind in this plan — if the frontend needs something the backend doesn't provide, that's a new backend plan, not a scope-creep addition here

## SCOPE LIMITS
- No calendar grid UI — that's 02-05
- No booking form — that's 02-06
- No httpOnly-cookie-based auth, no refresh-token flow — matches the backend's existing stateless-JWT-with-12h-expiry design (PROJECT.md's already-accepted tradeoff); revisit only if the backend's auth model itself changes
- No password-reset/forgot-password flow — out of scope, not yet built anywhere in this project
- Dashboard page in this plan is a placeholder (shows logged-in user info only) — 02-05 replaces its content, doesn't rebuild routing/auth around it
- <!-- audit-added --> No CORS middleware added to the backend in this plan (would violate the "no backend changes" boundary above). The dev-server proxy (Task 1) makes this a non-issue for local development and for this plan's own checkpoint verification. **Known follow-up, not silently deferred:** once the frontend is actually deployed to a different origin than the backend (Vercel + Railway/Render, per PROJECT.md), the backend will need `cors()` configured to allow that origin, or every cross-origin fetch will be browser-blocked. Flagging now so it isn't rediscovered as a surprise at deploy time — belongs in whichever plan first handles real deployment, not this one.
- <!-- audit-added --> localStorage token storage is XSS-exposed by design (documented tradeoff above). This constraint holds only as long as the frontend never introduces `dangerouslySetInnerHTML`, unreviewed third-party script tags, or other raw-HTML-injection surfaces. Any future plan adding such a pattern must reassess this tradeoff, not silently inherit it.

</boundaries>
