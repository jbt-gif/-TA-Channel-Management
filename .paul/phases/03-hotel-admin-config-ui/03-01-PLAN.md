<objective>
## Goal
Backend CRUD API for hotel self-configuration: RoomType create/update/soft-delete, RatePlan create/update/soft-delete (nested under a RoomType), and hotel-level policy settings (downpayment %) — all scoped per hotel, admin-role gated.

## Purpose
ROADMAP.md Phase 3 goal: "Hotel staff self-configure their own room types and rate plans — no founder involvement required per hotel." Right now every RoomType/RatePlan in the system was created by hand-run scripts during Phase 1/2 dev seeding. This plan is the first time a hotel admin can create one through the product itself.

## Output
- `POST/PATCH/DELETE /api/room-types` (create, update, soft-delete)
- `POST /api/room-types/:roomTypeId/rate-plans`, `PATCH/DELETE /api/rate-plans/:id`
- `GET/PATCH /api/hotel/policy` (downpaymentPercent)
- New Hotel.downpaymentPercent column + DB CHECK constraint (0-100)
</objective>

<assumptions-requiring-review>
## Assumptions Requiring Review

1. **New room types seed with `availableCount: 0`.** `seedInventoryForRoomType()` derives `availableCount` from `Room.count()` — and this plan does not build physical-Room (label/unit) CRUD, because ROADMAP.md's Phase 3 scope explicitly lists only "Room type + rate plan CRUD" and "policy settings," not Room management. Practical effect: a hotel admin can create a brand-new room type through this UI, but it will show 0 availability (permanently "sold out") until Rooms are added some other way (currently only via the manual seed script used in Phase 1/2 dev work). This matches PROJECT.md's "first hotels onboarded white-glove, manually" stance, but if the intent is for hotel admins to be fully self-sufficient without founder involvement, physical Room management is a real gap — not addressed here, not currently scheduled in any named phase. Flagging for your review rather than silently expanding this plan's scope.
2. **Role gate: `HOTEL_ADMIN` and `SUPER_ADMIN` only.** `FRONT_DESK`/`HOUSEKEEPING` get 403 on all endpoints in this plan. Matches PROJECT.md's "self-service hotel admin UI" framing; not stated as an explicit requirement anywhere so flagging as an assumption, not a given.
3. **RatePlan `basePrice` edits do not retroactively rewrite existing `RatePlanDailyRate` rows.** Editing a rate plan's base price only changes the field used to seed *new* dates going forward (e.g. when the 365-day window rolls or a new rate plan is created); it does not bulk-update already-seeded per-date prices. Per-date price overrides remain untouched by design — this plan does not build a rate-calendar bulk-edit feature. If the expectation is "changing base price changes what guests are charged tomorrow," that needs a separate plan.
</assumptions-requiring-review>

<acceptance_criteria>

## AC-1: Admin can create a room type
```gherkin
Given a logged-in HOTEL_ADMIN
When they POST /api/room-types with { name, baseCapacity }
Then a RoomType is created scoped to their hotelId, 201 returned, and it appears in GET /api/room-types
And DailyInventory is seeded for it across the standard 365-day window (availableCount 0, since no Rooms exist yet)
```

## AC-2: Non-admin roles cannot configure
```gherkin
Given a logged-in FRONT_DESK or HOUSEKEEPING user
When they call any endpoint in this plan (create/update/delete room type or rate plan, update policy)
Then 403 Forbidden is returned and no data changes
```

## AC-3: Admin can update and soft-delete a room type
```gherkin
Given an existing RoomType owned by the admin's hotel
When they PATCH name/baseCapacity, or DELETE it
Then the update is reflected in GET /api/room-types; after DELETE the room type no longer appears in GET /api/room-types or its calendar endpoint, matching the deletedAt:null filtering already used everywhere else
```

## AC-4: Admin can create a rate plan that is immediately bookable
```gherkin
Given an existing RoomType owned by the admin's hotel
When they POST /api/room-types/:roomTypeId/rate-plans with { name, isRefundable, includesBreakfast, basePrice }
Then a RatePlan is created, 201 returned, and RatePlanDailyRate rows are seeded for it across the same 365-day window at basePrice
And GET /api/room-types/:roomTypeId/calendar shows real prices for this rate plan immediately, not "No rate set"
```

## AC-5: Admin can update and soft-delete a rate plan
```gherkin
Given an existing RatePlan owned by the admin's hotel
When they PATCH its fields, or DELETE it
Then updates are reflected; after DELETE it no longer appears in GET /api/room-types or the calendar, and new bookings against it 404 (reusing bookings.ts's existing deletedAt:null lookup — no change needed there)
```

## AC-6: Cross-tenant access is a byte-identical 404
```gherkin
Given a HOTEL_ADMIN of Hotel A
When they PATCH/DELETE a room type or rate plan belonging to Hotel B, or POST a rate plan under a Hotel-B roomTypeId
Then the response is the identical 404 body used for "doesn't exist at all" — matching the tenant-isolation pattern already established in roomTypes.ts and bookings.ts
```

## AC-7: Admin can view and update hotel policy settings
```gherkin
Given a logged-in HOTEL_ADMIN
When they GET /api/hotel/policy, then PATCH it with a new downpaymentPercent
Then GET returns the current value; PATCH with 0-100 succeeds and persists; PATCH with a value outside 0-100 (or non-integer) returns 400
And a DB-level CHECK constraint backstops the 0-100 range regardless of application-layer validation
```

<!-- audit-added: must-have finding 1 (deletion-safety gap) -->
## AC-8: Deleting a room type or rate plan with future bookings is blocked
```gherkin
Given a RoomType or RatePlan that has at least one BookingItem for a future (today-or-later, Manila-anchored) stay on a non-cancelled booking
When an admin attempts to DELETE it
Then the request is rejected with 409 Conflict and a clear message, and the record remains active
And a RoomType/RatePlan with no future non-cancelled bookings deletes normally (200)
```

<!-- audit-added: strongly-recommended finding 2 (accountability trail) -->
## AC-9: Configuration changes carry an accountability trail
```gherkin
Given any successful create, update, or delete on a room type or rate plan
When the record is inspected afterward
Then it carries the acting user's id (lastModifiedByUserId on create/update, deletedByUserId on delete) — matching the createdByUserId/processedByUserId precedent already established on Booking/Payment in Phase 1
```
