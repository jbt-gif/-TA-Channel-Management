<objective>
## Goal
Detect local-origin rate/availability changes (admin sets otaPrice/basePrice, front desk creates a walk-in booking) and durably queue them for push — the input 04-04's background worker will consume. No push actually happens in this plan; this is change-tracking only.

## Purpose
04-02 proved the push mechanism works when called manually. Nothing calls it automatically yet. Before building the worker (04-04) that respects Channex's 10 req/min/property limit, there must be a durable record of *what changed and needs pushing* — a DB table, not an in-memory list, so a worker restart or crash never silently loses a pending change (same "DB is the real backstop" principle this project has applied to every other correctness-critical mechanism).

## Output
- `PushQueue` model — durable record of pending/processing/done/failed pushes, `PushQueueType` (AVAILABILITY/RATE), `PushQueueStatus` (PENDING/PROCESSING/DONE/FAILED)
- `src/routes/ratePlans.ts` — PATCH now accepts `otaPrice`, enqueues a RATE push on otaPrice/basePrice change
- `src/routes/bookings.ts` — walk-in booking creation enqueues an AVAILABILITY push
- Explicit non-change: `src/routes/channexWebhook.ts` untouched — webhook-originated inventory changes must never re-enqueue a push back to Channex
</objective>

<acceptance_criteria>

## AC-1: A local rate change enqueues a RATE push
```gherkin
Given a RatePlan mapped via ChannelMapping (RATE_PLAN) on a hotel with channexPropertyId set
When its otaPrice or basePrice is changed via PATCH /api/rate-plans/:ratePlanId
Then exactly one PENDING PushQueue row is created with type=RATE, ratePlanId set, dateFrom=today, dateTo=today+365 days
```

## AC-2: A local availability change enqueues an AVAILABILITY push
```gherkin
Given a RoomType mapped via ChannelMapping (ROOM_TYPE) on a hotel with channexPropertyId set
When a walk-in booking is successfully created via POST /api/bookings for that room type
Then exactly one PENDING PushQueue row is created with type=AVAILABILITY, roomTypeId set, dateFrom=checkInDate, dateTo=checkOutDate
```

## AC-3: No channel mapping means no queue noise
```gherkin
Given a RoomType/RatePlan with no ChannelMapping, or a hotel with no channexPropertyId
When the same mutations occur
Then no PushQueue row is created — nothing is connected to Channex yet, so nothing should queue
```

## AC-4: Webhook-originated changes never re-enqueue a push
```gherkin
Given an incoming Channex webhook processes booking_new/booking_modification/booking_cancellation and changes DailyInventory via channexWebhook.ts's increment/decrementInventory
When that inventory change happens
Then no PushQueue row is created — pushing back data Channex just told us would be redundant and waste the 10 req/min/property budget
```

## AC-5: A failed mutation never enqueues a push
```gherkin
Given a booking creation fails (sold out 409, validation 400, duplicate-submission guard)
When the request errors
Then no PushQueue row is created — only a genuinely committed change queues a push
```

<task type="auto">
  <name>Task 2: Wire enqueue at the two local-origin mutation points</name>
  <files>src/routes/ratePlans.ts, src/routes/bookings.ts</files>
  <action>
    **`src/routes/ratePlans.ts`** (PATCH handler, currently only accepts `basePrice`): add `otaPrice` as an acceptable body field, mirroring `basePrice`'s exact validation — must be a positive number if provided, but also accept an explicit `null` to clear it back to unset (matching the field's nullable schema; `basePrice` has no such clear-path since it's required, so this is a genuinely new branch, not a copy-paste of `basePrice`'s check).

    After the RatePlan update commits: if this PATCH's `data` included `otaPrice` and/or `basePrice`, AND a `ChannelMapping` exists for `{ hotelId, mappingType: "RATE_PLAN", ratePlanId }`, AND the hotel's `channexPropertyId` is non-null — create one `PushQueue` row: `type: "RATE"`, `ratePlanId`, `dateFrom` = today (Asia/Manila, reuse this file's or a shared today-string helper — do not introduce a second timezone calculation), `dateTo` = today + 365 days. This flat 365-day window matches `otaPrice`'s existing flat-value design (04-02: one value pushed regardless of date) and this project's existing 365-day inventory-seed horizon — not a new number invented for this plan.

    **`src/routes/bookings.ts`** (POST handler, after `prisma.$transaction(...)` resolves successfully): if a `ChannelMapping` exists for `{ hotelId, mappingType: "ROOM_TYPE", roomTypeId }`, AND the hotel's `channexPropertyId` is non-null — create one `PushQueue` row: `type: "AVAILABILITY"`, `roomTypeId`, `dateFrom: checkInDate`, `dateTo: checkOutDate` (the exact stay range already computed earlier in this handler).

    In both places: the enqueue insert happens as its own write **after** the triggering mutation has already committed — never inside the same transaction, and its failure must never roll back or fail the response for a mutation that already succeeded. Wrap the enqueue insert in its own try/catch; on failure, `console.error` and still return the original success response. A missed queue row is a recoverable gap (04-04 or a future reconciliation pass can re-derive it); a rolled-back booking or price change over a queue-table hiccup would not be.

    **Do not modify `src/routes/channexWebhook.ts`.** Its `incrementInventory`/`decrementInventory` calls are webhook-originated — enqueueing a push there would tell Channex about a change it just told *us* about, wasting the rate-limit budget for zero benefit. This is a boundary, not an oversight (see AC-4).

## SCOPE LIMITS
- No worker/poller — this plan only writes `PushQueue` rows. Nothing ever consumes or transitions them yet; that is 04-04's entire job.
- No retry/backoff logic — belongs to the worker that actually performs pushes, not the code that detects a change happened.
- No general `otaPrice` admin UI/UX — only the minimal PATCH body-field acceptance needed to create a real trigger point for this plan's own verification. A proper admin form (03-02-style) for setting markup remains a future, unnamed plan.
- No booking modification/cancellation wiring — no such local (non-webhook) endpoint exists yet in this codebase; only booking *creation* is wired.
