<objective>
## Goal
Resolve the agency-model schema gap (hotel base rate vs. marked-up OTA listing price) and build a working, live-proven Channex API client that pushes availability and rate/restriction data — the foundation 04-03's automatic worker will call.

## Purpose
ROADMAP.md flags that `RatePlan.basePrice` is a single field, but the agency model needs to push the OTA's *marked-up* listing price to Channex, not the hotel's raw base rate — pushing `basePrice` directly would push the hotel's own rate, giving away the agency's margin. This plan resolves that gap and proves the actual Channex push mechanism works against the real staging API, before 04-03 wires it into automatic triggers.

## Output
- `RatePlan.otaPrice` — nullable Decimal, independent from `basePrice` (user-confirmed schema choice: separate field, not a computed markup)
- `src/lib/channex.ts` extended with `pushAvailability` and `pushRestrictions` — thin, rate-limit-aware wrappers around Channex's two ARI endpoints
- Live proof: a real push lands in Channex's staging dashboard for the test hotel already wired in 04-01
</objective>

## AC-1: A rate plan's OTA listing price is stored independently from its base rate
```gherkin

When otaPrice is set to a different value

```

## AC-2: Pushing availability updates Channex's real availability for a room type/date range
```gherkin
Given a hotel with channexPropertyId set and a RoomType mapped via ChannelMapping to a real Channex room_type_id
When pushAvailability is called with that room type and a date range plus an availability count
Then a real POST to Channex's staging /api/v1/availability succeeds, and the pushed value is confirmable via Channex's own API/dashboard for that property
```

## AC-3: Pushing restrictions updates Channex's real rate for a rate plan/date range
```gherkin
Given a RatePlan mapped via ChannelMapping to a real Channex rate_plan_id, with otaPrice set
When pushRestrictions is called for that rate plan and a date range
Then a real POST to Channex's staging /api/v1/restrictions succeeds using otaPrice (not basePrice) as the pushed rate, confirmable via Channex's own API/dashboard
```

## AC-4: A rate plan with no otaPrice set falls back to basePrice, not a push failure
```gherkin
Given a RatePlan with otaPrice = null
When pushRestrictions is called for that rate plan
Then the push uses basePrice as the rate (documented fallback, not silent 0 or a thrown error) — logged clearly that a fallback occurred, since this likely means the OTA markup hasn't been configured yet for this rate plan
```

## AC-5: A push failure surfaces clearly, not silently
```gherkin
Given a Channex API call fails (4xx/5xx, network error, or rate-limited)
When pushAvailability or pushRestrictions is called
Then the function throws a typed error identifying which push failed and why — never swallows the failure or returns a false-success
```
