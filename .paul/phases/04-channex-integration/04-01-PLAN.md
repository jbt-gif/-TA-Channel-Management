<objective>
## Goal
Receive and process Channex webhook events for new/modified/cancelled OTA bookings — verified authentic, idempotent on retry, and safely decrementing the same shared inventory walk-in bookings use.

## Purpose
This is the first half of ROADMAP.md's Phase 4 goal ("incoming bookings create reservations atomically"). Per RESEARCH.md, Channex webhooks are thin notifications only — the real work is verifying the request, pulling the full booking revision from Channex's API, mapping it to our tenant-scoped models via `ChannelMapping`, and reusing the same overbooking-safe transaction pattern already proven in Phase 2 (02-03).

## Output
- `Hotel.channexPropertyId` field (links a hotel to its Channex property UUID) + migration
- `src/lib/channex.ts` — thin API client: pull a booking revision by ID, verify the webhook's shared-secret header
- `src/routes/channexWebhook.ts` — `POST /api/webhooks/channex`, mounted in `src/app.ts`
- `.env.example` updated with the three new Channex env vars
</objective>

## AC-2: A hotel can be linked to its Channex property
```gherkin
Given the Hotel model
When channexPropertyId is set on a hotel record
Then that hotel can be looked up by Channex's property_id (used to route incoming webhooks and scope outgoing ARI pushes in 04-02)
```

## AC-3: An authentic webhook creates a real booking, decrementing shared inventory the same way a walk-in does
```gherkin
Given a hotel with channexPropertyId set, a RoomType/RatePlan with a matching ChannelMapping row, and available inventory for the stay dates
When a POST to /api/webhooks/channex arrives with the correct shared-secret header and a booking_new event referencing that property/room/rate
Then the handler pulls the full booking revision from Channex's API, creates a Booking (source: OTA, externalBookingId: the revision's id) + BookingItem(s) with a real guest record, and DailyInventory.bookedCount increments using the exact same conditional-UPDATE transaction pattern as 02-03 (SoldOutError on a 409 if inventory is already gone)
```

## AC-4: An inauthentic request is rejected before any data is touched
```gherkin
Given a POST to /api/webhooks/channex missing or with an incorrect shared-secret header
When the request arrives
Then it is rejected 401 before any database read/write occurs
```

## AC-5: A retried webhook for the same booking revision is not double-processed
```gherkin
Given a booking_new webhook was already successfully processed for revision X (Booking.externalBookingId = X exists)
When Channex retries the same event (per RESEARCH.md, retries happen on any 5xx and delivery order isn't guaranteed)
Then the handler detects the existing Booking by externalBookingId and returns 200 without creating a duplicate booking or double-decrementing inventory
```

## AC-6: A modification or cancellation event updates the existing booking, not create a new one
```gherkin
Given an existing Booking with externalBookingId = X (source: OTA)
When a booking_modification or booking_cancellation webhook arrives for revision-chain X
Then the existing Booking is updated (cancellation sets status: CANCELLED and releases the held inventory; modification updates dates/amount) rather than a second Booking being created
```

## AC-7: An unmapped room type or rate plan fails loudly, not silently
```gherkin
Given a booking_new event whose Channex room_type_id or rate_plan_id has no matching ChannelMapping row for that hotel
When the handler processes it
Then it responds with a distinct error status and logs a clear message identifying the missing mapping — never silently drops the booking or guesses a mapping
```

## AC-8: Every code path returns 200 to Channex once the event is durably handled or safely rejected, per their retry-on-5xx behavior
```gherkin
Given any of AC-3 through AC-7's scenarios
When the handler finishes
Then it returns 200 for successfully processed or already-processed-idempotent cases, and a genuine 4xx/5xx only for cases that should actually trigger Channex's retry-or-alert behavior (auth failure, unmapped resource, real server error) — not a blanket "always 200" that would hide real failures from Channex's own retry/alerting
```

<!-- audit-added: must-have finding 1 -->
## AC-9: Two concurrent retries of the same webhook never create two Booking records
```gherkin
Given Channex has already retried the same booking_new event before the first attempt finished processing (per RESEARCH.md, retries happen on any 5xx and Channex doesn't wait for prior attempts to complete)
When both requests reach the idempotency check at nearly the same time
Then a DB-level unique constraint (not just the application-level findFirst check) guarantees at most one Booking is created for that externalBookingId — the second request's unique-constraint violation is caught and treated as the idempotent-no-op case, not a 500
```

<!-- audit-added: must-have finding 2 -->
## AC-10: A booking_modification that changes dates or rooms is either fully applied or fully rolled back — never left half-done
```gherkin
Given an existing OTA Booking with externalBookingId X
When a booking_modification webhook arrives whose pulled revision has different checkin/checkout dates or a different room_type_id than the existing Booking
Then the cancel-old-and-create-new sequence runs inside one Prisma $transaction so a failure partway through (e.g. the new dates are sold out) rolls back cleanly, leaving the ORIGINAL booking intact and unmodified, with the conflict logged clearly for manual follow-up — never a state where the old booking is gone but no new one exists
```

<task type="auto">
  <name>Task 2: Webhook handler — booking_new/modification/cancellation, idempotent, tenant-mapped</name>
  <files>src/routes/channexWebhook.ts, src/app.ts</files>
  <action>
    Create `channexWebhookRouter` with `POST /`, mounted at `/api/webhooks/channex` in `app.ts` (no `requireAuth` — this endpoint uses `verifyWebhookSecret` instead, Channex is the caller, not a logged-in user). <!-- audit-added: strongly-recommended finding 6 --> Mount this route with its own `express.json({ limit: '256kb' })` body parser, scoped to just this route (do not change the global `app.use(express.json())` default in `app.ts` — this is defense-in-depth against an oversized/malformed request hitting this specific internet-facing, lighter-auth endpoint, not a change to any other route's behavior).

    <!-- audit-added: strongly-recommended finding 10 --> **Structured log shape:** every log line this handler emits (success, no-op, and error cases alike) must include `{ hotelId, event, revisionId, outcome }` at minimum — not free-text messages that vary per call site. This is what makes incident reconstruction possible later without guessing what got logged at the time.

    Handler flow:
    1. Call `verifyWebhookSecret(req)` first, before touching the body or DB. Fail closed: missing/wrong secret → 401, nothing else runs (AC-4).
    2. Parse the thin event body (`event`, `payload.booking_id`, `payload.revision_id`, `property_id`, per RESEARCH.md's documented shape). If `event` isn't one of `booking_new`/`booking_modification`/`booking_cancellation`, return 200 immediately (Channex sends many other event types this endpoint doesn't need to act on — acknowledging and no-opping is correct, not an error).
    3. Look up the hotel: `prisma.hotel.findFirst({ where: { channexPropertyId: property_id, deletedAt: null } })`. Not found → log clearly, respond 200 (an unmapped property on OUR side isn't Channex's problem to retry over — matches the "no blanket 200" AC-8 nuance: this is a legitimate no-op case, not a failure to hide).
    4. **Idempotency check (AC-5):** `prisma.booking.findFirst({ where: { hotelId, externalBookingId: payload.revision_id } })`. If found and event is `booking_new`, return 200 without reprocessing.
    5. Call `pullBookingRevision(payload.revision_id)` to get the full data. <!-- audit-added: strongly-recommended finding 4 --> **Validate the response before using it**: `rooms[]` must be non-empty, each room must have `room_type_id`/`rate_plan_id`/`checkin_date`/`checkout_date`; treat `customer.mail` as absent for guest-matching purposes if it's missing, `null`, OR an empty string (three different falsy shapes Channex's API could plausibly return — don't assume only `undefined`). Fail with a clear typed error (not a downstream crash from e.g. calling `.find()` on `undefined`) if the pulled revision is malformed.
    6. Map each `rooms[]` entry's `room_type_id`/`rate_plan_id` to this hotel's `ChannelMapping` rows (`externalId` match, scoped by `hotelId`). Any room with no mapping → AC-7: respond with a distinct status (409 is reasonable — this is a real conflict between what Channex thinks exists and what we have configured) and a log line naming the missing external ID, do not partially process the booking.
    7. **booking_new:** run the same conditional-UPDATE-per-date transaction pattern as `bookings.ts`'s `POST /` (reuse the `SoldOutError` shape), creating a `Guest` (find-or-create by email within the hotel, same as `bookings.ts`) and a `Booking` with `source: "OTA"`, `status: "CONFIRMED"`, `externalBookingId: revision_id`, <!-- audit-added: strongly-recommended finding 5 --> `createdByUserId: null` (explicit, with a code comment: no human user initiated this booking — it's system-created from a Channex webhook; `createdByUserId` stays nullable precisely for this case per its original Phase-1 design), plus `BookingItem`(s) built from `rooms[]`. <!-- audit-added: must-have finding 1 --> If the `Booking.create` call fails with a Prisma unique-constraint violation (error code `P2002` on the new partial unique index), treat this exactly like the idempotency no-op case in step 4 — a concurrent retry beat this request to the insert — and return 200, not 500. On `SoldOutError`, this is a genuine problem (Channex thinks a room is available that we don't have) — log it clearly (per the structured log shape above) as a sync-conflict for future investigation, still return 200 to Channex (retrying won't fix an inventory conflict) rather than triggering their retry loop for something retries can't resolve.
    8. **booking_cancellation:** find the existing `Booking` by `externalBookingId`, set `status: "CANCELLED"`, and in the same transaction decrement `DailyInventory.bookedCount` back down for each affected date (mirroring the increment logic, inverted) so the room becomes bookable again.
    9. **booking_modification:** find the existing `Booking`. <!-- audit-added: must-have finding 2 --> If the room/rate-plan and date range are UNCHANGED from the pulled revision, just update the amount/notes fields in a simple `Booking.update` — no inventory impact. If the room OR dates HAVE changed (AC-10): inside **one** `$transaction`, (a) release the old booking's inventory (same decrement logic as cancellation) and mark it `CANCELLED` with a note referencing the replacement, (b) attempt the new dates' conditional-UPDATE increment and create the replacement `Booking`/`BookingItem`(s) with the same `externalBookingId` (the unique index from Task 1 means this replacement booking needs a distinguishable identifier — append a suffix or use a separate `previousBookingId` link field rather than reusing the exact same `externalBookingId` twice; decide and document the concrete approach in code, don't leave it implicit), (c) if step (b)'s `SoldOutError` fires, let the transaction roll back entirely — step (a)'s cancellation is undone too, the ORIGINAL booking survives untouched, and the conflict is logged clearly for manual follow-up. Never a state where the transaction partially commits.
    10. Wrap all DB/Channex-API work in try/catch matching this project's established discipline (02-02's audit fix: the try/catch must cover the tenant lookup too, not just the transaction). Real unexpected errors (Channex API down, DB error) → 500, which DOES trigger Channex's legitimate retry — this is the one case where letting their retry mechanism work is correct.
  </action>
