<objective>
## Goal
Consume `PushQueue` (04-03) automatically — no human running a script — calling `pushAvailability`/`pushRestrictions` (04-02) while staying under Channex's 10 req/min/property limit, with real retry/failure handling.

## Purpose
04-02 proved the push mechanism works when called manually. 04-03 proved changes get durably recorded. Nothing has ever consumed that queue — this plan closes the loop the phase's own goal describes: rate/availability changes push out automatically. This is also the plan where "did the push actually work" first needs a genuine answer beyond "the HTTP call returned 200" — a background worker fails unattended, so failures must be visible (attempts, lastError, a terminal FAILED state) rather than silently retried forever or silently dropped.

## Output
- `src/lib/pushQueueWorker.ts` — `runPushQueueTick()` (one poll cycle) and `startPushQueueWorker()` (the interval loop)
- `src/server.ts` starts the worker — explicitly NOT `src/app.ts`, so importing the Express app for tests/scripts never spins up a background interval as a side effect
- Live proof: a real local change (not a manual push-client call) shows up on Channex's staging dashboard within one poll cycle, unattended
</objective>

<acceptance_criteria>

## AC-1: A PENDING RATE row is processed and pushed with a freshly-read value
```gherkin
Given a PENDING PushQueue row of type RATE for a mapped, connected rate plan
When one poll cycle (runPushQueueTick) runs
Then pushRestrictions is called with the rate plan's CURRENT otaPrice (or basePrice if otaPrice is null), read at push time — not any value cached when the row was enqueued — and the row's status becomes DONE
```

## AC-2: A PENDING AVAILABILITY row is processed and pushed with a freshly-read value
```gherkin
Given a PENDING PushQueue row of type AVAILABILITY for a mapped, connected room type
When one poll cycle runs
Then pushAvailability is called with the CURRENT minimum free count (availableCount - bookedCount - heldCount) across the row's date range, read at push time, and the row's status becomes DONE
```

## AC-3: A genuinely failing push retries, then terminates
```gherkin
Given a PENDING row whose push will genuinely fail (e.g. Channex rejects the mapped external id)
When it fails on successive poll cycles
Then each failure increments attempts and records lastError, the row returns to PENDING between attempts, and once attempts reaches the cap the row is marked FAILED and is never retried again
```

## AC-4: Claiming is atomic and terminal states are final
```gherkin
Given a row already DONE or FAILED, or a row currently PROCESSING
When another poll cycle runs
Then that row is never re-processed — only PENDING rows are claimed, and claiming a row is a single atomic UPDATE (no double-processing if two ticks overlap)
```

## AC-5: A real local change is pushed automatically, with no manual script call
```gherkin
Given the real server running (worker started via server.ts)
When a rate or availability change is made through the actual API (not a script calling pushAvailability/pushRestrictions directly)
Then the change appears on Channex's staging dashboard within one poll cycle, without any human or script invoking the push client
```

  <name>Task 1: PushQueue worker core</name>
  <files>src/lib/pushQueueWorker.ts</files>
  <action>
    Create `src/lib/pushQueueWorker.ts`:

    - `MAX_ATTEMPTS = 5` (module constant).
    - `claimNextPending(hotelId: string): Promise<PushQueue | null>` — claims at most one row per call via a conditional atomic UPDATE (`UPDATE "PushQueue" SET status='PROCESSING' WHERE id = (SELECT id FROM "PushQueue" WHERE "hotelId" = $1 AND status = 'PENDING' ORDER BY "createdAt" ASC LIMIT 1) RETURNING *`, or equivalent Prisma `$queryRaw`/`$executeRaw` pairing) — same "the UPDATE and the check are the same statement" principle this project already uses for inventory (02-03, 04-01's decrementInventory), applied here to prevent two overlapping ticks from double-claiming.
    - `computeRateValue(ratePlanId: string): Promise<string | null>` — fresh `prisma.ratePlan.findUnique`, returns `(otaPrice ?? basePrice).toString()`, or `null` if the rate plan no longer exists (deleted since enqueue).
    - `computeAvailabilityValue(hotelId: string, roomTypeId: string, dateFrom: Date, dateTo: Date): Promise<number | null>` — fresh `prisma.dailyInventory.findMany` for that room type across the date range, returns the MINIMUM of `availableCount - bookedCount - heldCount` across all matched dates (conservative: never overstate availability for any date in the range — this project has no per-date availableCount variance yet since Room OOS/CRUD isn't wired to availability, see the existing Deferred Issue; if that ever changes, this minimum-across-range approach will need revisiting, not this plan's job to solve). Returns `null` if no DailyInventory rows are found (shouldn't happen for a real room type, but never divide-by-nothing).
    - `resolveExternalIds(hotelId, roomTypeId?, ratePlanId?)` — fresh `ChannelMapping` + `Hotel.channexPropertyId` lookup at push time (never trust anything cached from enqueue time). Returns `null` if the hotel is no longer connected or the mapping no longer exists (deleted since enqueue) — this is a genuine "nothing to push to anymore" case, not a retryable failure.
    - `processRow(row)`: claim already happened by the caller. If `resolveExternalIds` or the value-compute function returns `null`, mark the row FAILED immediately with a clear `lastError` (not retryable — the target no longer exists). Otherwise call `pushAvailability`/`pushRestrictions` per `row.type`. On success: `status: DONE`. On `ChannexApiError`/any thrown error: increment `attempts`, set `lastError` to the error message; if `attempts >= MAX_ATTEMPTS` set `status: FAILED`, else set `status: PENDING` (eligible for the next tick). A 429 (`err.status === 429` on `ChannexApiError`) still counts toward `attempts` — this project's tick cadence (Task 2) is designed to stay under the limit on its own; a 429 anyway signals something worth surfacing via `lastError`, not silently absorbing forever.
    - `runPushQueueTick(): Promise<void>` — fetch all hotels with non-null `channexPropertyId`, for each call `claimNextPending` then `processRow` if a row was claimed (at most one row per hotel per tick — this bound is what keeps the worker under 10 req/min/property once Task 2 sets the interval, without needing a separate per-property rate-limiter).
  </action>

## SCOPE LIMITS
- No sync status UI / staff alerts — that's 04-05. This plan's only visibility into failures is the `PushQueue` row itself (`status`, `attempts`, `lastError`), queryable but not yet surfaced anywhere a human looks by default.
- No exponential backoff/jitter — the fixed 7-second tick cadence is the only pacing mechanism. Sufficient for this pilot's low volume; revisit only if real usage ever approaches the rate limit in practice.
- No distributed-locking / multi-instance safety beyond the single atomic claim UPDATE — this project runs one backend process today (see PROJECT.md tech stack), so cross-instance coordination is out of scope until that changes.
- No manual admin "retry a FAILED row" action — a FAILED row stays FAILED until a future plan (likely 04-05, or a dedicated ops action) adds one.

</boundaries>
