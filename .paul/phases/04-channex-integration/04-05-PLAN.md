<objective>
## Goal
Give hotel admins a visible way to see Channex sync health and manually retry a failed push — closing the gap 04-04 flagged: a `FAILED` `PushQueue` row currently has no human-visible surface and no retry action.

## Purpose
This is the last plan in Phase 4 and the one ROADMAP.md's phase goal names explicitly: "staff see sync status and get alerted on failure." 04-02/04-03/04-04 built a fully working, unattended push pipeline — but if a mapping breaks or a rate plan gets deleted, the only trace today is a `FAILED` row a founder would have to query the database directly to find. This plan surfaces that.

## Output
- `GET /api/sync-status` — per-hotel counts by status + the list of `FAILED` rows with their error
- `POST /api/sync-status/:id/retry` — resets one `FAILED` row back to `PENDING` so the worker picks it up again
- A dashboard indicator (badge, not just backend logs) when failures exist, linking to a dedicated sync-status page
</objective>

<acceptance_criteria>

## AC-1: Admin sees a status summary for their hotel
```gherkin
Given a hotel with PushQueue rows in various statuses
When a HOTEL_ADMIN/SUPER_ADMIN calls GET /api/sync-status
Then the response includes accurate counts of PENDING/PROCESSING/DONE/FAILED rows for that hotel only
```

## AC-2: Admin sees the actionable failure list
```gherkin
Given a hotel with at least one FAILED PushQueue row
When a HOTEL_ADMIN/SUPER_ADMIN calls GET /api/sync-status
Then the response includes that row's type, roomTypeId/ratePlanId, date range, attempts, and lastError
```

## AC-3: Admin can retry a failed push
```gherkin
Given a FAILED PushQueue row belonging to the admin's hotel
When the admin calls POST /api/sync-status/:id/retry
Then the row's status becomes PENDING, attempts resets to 0, and 04-04's worker picks it up on its next tick — lastError is left untouched (see AC-8)
```

## AC-4: A failure state is visible without querying the database
```gherkin
Given a hotel with at least one FAILED PushQueue row
When an admin views the Dashboard
Then a visible indicator (not hidden in logs) shows a failure exists and links to the sync-status page
```

## AC-5: Tenant isolation holds
```gherkin
Given two hotels, each with their own PushQueue rows
When an admin from Hotel A requests GET /api/sync-status or POST /api/sync-status/:id/retry using Hotel B's row id
Then Hotel A's admin never sees Hotel B's data, and the retry attempt returns 404 (not 403, matching this project's existing cross-tenant-lookup pattern of a byte-identical not-found response — see roomTypes.ts/bookings.ts precedent)
```

## AC-6: Non-admin roles are blocked
```gherkin
Given a FRONT_DESK or HOUSEKEEPING user
When they call GET /api/sync-status or POST /api/sync-status/:id/retry
Then both return 403 — sync health/retry is an admin/ops concern, same role gate as Admin.tsx's existing CRUD endpoints
```

## AC-7: A retry is accountable and cannot be used to bypass the worker's retry cap <!-- audit-added -->
```gherkin
Given a FAILED PushQueue row was just retried by an admin
When another retry is attempted on the same row within 60 seconds
Then the second attempt returns 409 (not a fresh reset) — retriedByUserId and lastRetriedAt from the first retry remain the recorded accountability trail, and attempts cannot be reset to 0 in a tight loop to defeat 04-04's MAX_ATTEMPTS circuit breaker
```

## AC-8: Retrying never destroys the evidence of what failed <!-- audit-added -->
```gherkin
Given a FAILED row with a populated lastError from its last real push attempt
When an admin successfully retries it (outside the cooldown window)
Then lastError is left untouched — it still shows the last known failure reason until the NEXT real push attempt (success or failure) overwrites it, so "why did this fail before someone fixed it" remains reconstructable after the fact
```

<task type="auto">
  <name>Task 1b: Sync status API — summary, failure list, retry</name>
  <files>src/routes/syncStatus.ts, src/app.ts</files>
  <action>
    Create `src/routes/syncStatus.ts` mirroring `ratePlans.ts`'s exact conventions (`ADMIN_ROLES = new Set(["HOTEL_ADMIN", "SUPER_ADMIN"])`, try/catch around the whole handler, tenant-scoped `where: { hotelId }` on every query):

    - `GET /` — `requireAuth`, admin-only (403 otherwise). Returns `{ counts: { PENDING: n, PROCESSING: n, DONE: n, FAILED: n }, failed: [{ id, type, roomTypeId, ratePlanId, roomTypeName, ratePlanName, dateFrom, dateTo, attempts, lastError, updatedAt }] }`. Counts via `prisma.pushQueue.groupBy({ by: ["status"], where: { hotelId }, _count: true })` (fill in zero for any status with no rows — don't omit keys). `failed` via `prisma.pushQueue.findMany({ where: { hotelId, status: "FAILED" }, orderBy: { updatedAt: "desc" } })`. <!-- audit-added: strongly-recommended finding 3 --> **Resolve `roomTypeName`/`ratePlanName` by looking up the referenced `RoomType`/`RatePlan` (whichever is non-null on the row) — a bare cuid tells an admin nothing actionable; the name is what lets them recognize which listing actually broke.** If the referenced entity was since deleted, fall back to `"(deleted)"` rather than crashing or omitting the row. No pagination on `failed`; `FAILED` rows only accumulate when something is genuinely broken, so this list stays small in practice for this project's current single-pilot-hotel scale. If that assumption stops holding, add pagination then, not speculatively now.
    - `POST /:id/retry` — `requireAuth`, admin-only. Look up the row scoped to `{ id, hotelId }` (never a bare `{ id }` lookup — that would leak cross-tenant existence). Not found → 404 with the same generic body this project already uses for cross-tenant/nonexistent-id responses (`{ error: "Not found" }` or equivalent — match `ratePlans.ts`'s `RATE_PLAN_NOT_FOUND_BODY` pattern, byte-identical for both "belongs to another hotel" and "doesn't exist"). Found but `status !== "FAILED"` → 409 (`{ error: "Row is not in a retryable state" }`). <!-- audit-added: must-have finding 2 --> **Found and FAILED, but `lastRetriedAt` is within the last 60 seconds → 409 (`{ error: "Retried too recently, wait before trying again" }`) — this is the guard that stops a retry loop from repeatedly resetting `attempts` to 0 and defeating 04-04's MAX_ATTEMPTS circuit breaker against Channex's rate-limited (and, in production, paid) API.** Otherwise update `{ status: "PENDING", attempts: 0, retriedByUserId: userId, lastRetriedAt: new Date() }` — <!-- audit-added: must-have finding 1 --> **deliberately do NOT touch `lastError`.** Clearing it on retry would destroy the only record of what actually failed at the exact moment a human acts on it, directly undermining PROJECT.md's own named Success Metric ("Silent failures — zero, every failure visibly logged"). `lastError` stays as the last-known failure reason until the next real push attempt (via 04-04's worker) overwrites it with a fresh outcome. Return the updated row.

    Mount in `src/app.ts`: `app.use("/api/sync-status", syncStatusRouter);` alongside the other routers (after `express.json()`, same as `ratePlansRouter`/`bookingsRouter`).
  </action>
  <verify>
    Throwaway script (`npx tsx`, deleted after use) against the real dev DB, using two separate test hotels (reusing the pattern from 04-03's/04-04's verify scripts):
    - Create PushQueue rows across all 4 statuses for Hotel A, including one genuine FAILED row with a real `lastError`. GET as Hotel A's HOTEL_ADMIN → counts match, failed list contains the row with correct fields including a resolved `roomTypeName`/`ratePlanName` (not a bare id).
    - GET as a FRONT_DESK user → 403.
    - POST retry on Hotel A's FAILED row id, authenticated as Hotel B's admin → 404 (cross-tenant, byte-identical to a genuinely nonexistent id — assert both bodies match).
    - POST retry on Hotel A's FAILED row as Hotel A's admin → 200, row now PENDING/attempts=0/retriedByUserId=that admin's id/lastRetriedAt set, **lastError still populated with the original failure reason**.
    - Immediately POST retry again on the same (now-PENDING, not FAILED) row → 409 (not retryable — already covers the cooldown case too, but also test the cooldown directly: manually set the row back to FAILED with a recent `lastRetriedAt` and confirm retry within 60s → 409).
    - POST retry on a DONE row → 409.
  </verify>
